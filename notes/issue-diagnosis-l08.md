## 결론

제공된 Issue만으로는 작업을 시작하기 부족하다. 문제 범위와 완료 판정이 없고, “관리자 화면”은 현재 저장소의 API 구조와도 일치하지 않는다. 입력에 없는 내용은 추측해 채우지 않고 누락 정보와 사람 결정 필요 항목으로 남긴다.

## 문장별 분류

| 원문 | 주 분류 | 진단 |
| --- | --- | --- |
| `# 주문 상태 이상함` | 확인된 요청 | 요청 제목이지만 대상 상태·발생 조건·영향이 없어 검색과 범위 판정이 어려움 |
| “결제가 실패한 주문 처리가 이상합니다.” | 확인된 요청 | 문제 제기 자체는 확인되지만 실제 응답, 저장 상태와 재현 절차가 없어 어떤 동작이 이상한지는 코드로 확인해야 함 |
| “상태를 하나 추가하고 관리자 화면에도 보이게 고쳐 주세요.” | 확인된 요청 + 사람 결정 | 상태 추가와 관리자 노출을 함께 요구함. 어떤 상태와 노출 범위를 적용할지는 정책으로 대조해야 하며, “관리자 화면”이 기존 API인지 새 UI인지 사람이 결정해야 함 |
| “재고 문제도 같이 해결하면 좋겠습니다.” | 사람 결정 | 포함 여부와 대상 시나리오가 확정되지 않은 범위 표현임. 특정 재고 문제 하나로 축소하면 근거 없는 추정이 됨 |
| “최대한 빨리 반영해 주세요.” | 확인된 요청 + 사람 결정 | 긴급 의도는 확인되지만 기한, 배포 대상과 다른 작업 대비 우선순위는 사람이 정해야 함 |

### 코드로 확인할 사실

- 현재 주문 상태 타입에는 `payment_failed`가 없다.
- 결제 실패 시 실패 이력을 기록한 뒤 주문을 삭제하고 기본 HTTP 200과 `{ ok: false }`를 반환한다.
- 관리자 목록은 남아 있는 주문만 순회하므로 삭제된 실패 주문을 표시하지 못한다.
- 주문 생성 시 재고를 즉시 차감하며 재고 부족 검사와 동일 상품 수량 합산 검사가 없다.
- 현재 테스트는 주문·결제·관리자 흐름의 응답 일부만 확인하고 상태·저장·재고·실패 상세를 검증하지 않는다.

### 근거 없는 추정으로 남길 내용

- “관리자 화면”이 새 UI를 뜻한다고 단정하는 것
- “재고 문제”를 생성 시 부족, 결제 시 부족, 중복 항목 또는 중복 차감 중 하나로 임의 축소하는 것
- 입력에 없는 API 응답 필드, 오류 메시지, 일정과 배포 범위를 정하는 것
- 정책에서 보류한 동작을 허용 또는 금지로 확정하는 것

## 누락 정보

- 재현할 API 요청과 준비 상태
- 실제 응답·주문 상태·재고 값
- 기대 결과와 완료 조건
- 대상 엔드포인트와 관리자 API/UI 범위
- “재고 문제”가 가리키는 구체적인 시나리오
- 실패정보의 응답 필드와 안전한 실패 사유 형식
- 재결제 거부 시 HTTP 상태와 메시지
- 결제 시점 재고 부족의 주문 상태와 응답
- 필요한 테스트 시나리오와 검증 명령
- 우선순위, 목표 날짜 또는 배포 범위

## 정책 근거와 현재 코드

| 영역 | 정책상 확인된 목표 | 현재 코드 |
| --- | --- | --- |
| 실패 상태 | `pending → payment_failed`, 주문과 실패 이력 보존 | `OrderStatus`에 `payment_failed`가 없고 실패 시 주문을 삭제함 |
| 실패 응답 | HTTP 402와 실패정보. 카드 정보와 내부 오류·예외 메시지·스택은 외부 노출에서 제외 | HTTP 200과 `{ ok: false }`만 반환하며 실패 사유 필드가 없음 |
| 재결제 | 동일한 `payment_failed` 주문의 재결제 금지 | 현재는 주문이 삭제되어 재결제 대상 자체가 사라짐 |
| 관리자 조회 | 보존된 `payment_failed` 주문에 상태·금액·시각·안전한 실패 사유 표시 | 남아 있는 주문만 순회하므로 실패 주문이 누락되고 실패 사유도 저장되지 않음 |
| 재고 | 동일 상품 수량을 합산해 생성 전에 검사하고, 생성 시 미차감·결제 성공 시 한 번만 차감 | 생성 시 즉시 차감하며 부족 검사와 상품별 합산 검사가 없음 |
| 검증 | 실패 주문 보존·조회, 재고 불변, 재결제 거부, 관리자 실패정보 검증 필요 | 테스트는 응답 상태 일부와 배열 여부만 확인함 |

정책으로 확정되지 않은 항목도 있다. 결제 시점 재고 부족의 상태·응답, 기술적 재시도, 복수 실패 이력의 관리자 표시 기준은 사람의 결정 전까지 구현할 수 없다.

## 사람이 답할 질문

1. “관리자 화면”은 기존 `GET /admin/orders` API 변경을 뜻하는가, 별도 UI까지 뜻하는가?
2. 이번 Issue는 결제 실패 흐름만 다루는가, 주문 생성과 결제 성공의 재고 차감 시점까지 포함하는가?
3. 재고 문제는 생성 시 부족, 결제 시점 부족, 동일 상품 중복 항목, 중복 차감 중 어느 시나리오를 포함하는가?
4. 결제 실패 응답에 포함할 안전한 실패 사유의 필드명과 허용 값은 무엇인가?
5. `payment_failed` 주문의 재결제 거부 시 HTTP 상태와 응답 메시지는 무엇인가?
6. 결제 시점에 재고가 부족하면 주문 상태와 결제 응답을 어떻게 유지할 것인가?
7. 같은 주문에 실패 이력이 여러 개라면 관리자 목록에는 어느 이력을 표시할 것인가?
8. 완료로 판정할 필수 테스트와 목표 일정은 무엇인가?
