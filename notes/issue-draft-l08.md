## Summary

결제 실패 주문을 별도 상태로 보존하고 관리자 조회에서 확인할 수 있도록 한다. 관리자 제공 방식과 함께 처리할 재고 문제의 범위는 아직 결정이 필요하다.

## Context

제공된 요청은 결제 실패 주문의 상태 추가, 관리자 노출과 재고 문제 해결을 요구하지만 재현 조건과 구체적인 범위를 제시하지 않는다. 현재 구현은 실패한 결제 시도를 기록한 뒤 주문을 삭제하며, 장기 정책은 실패 주문과 이력을 보존하도록 요구한다.

## Current Behavior

- 주문 상태 타입은 `pending`, `paid`, `cancelled`만 지원한다.
- `pending` 주문의 결제가 실패하면 실패 시도를 기록하고 주문을 삭제한 뒤 HTTP 200과 `{ "ok": false }`를 반환한다.
- 관리자 주문 목록은 저장된 주문만 순회하므로 삭제된 실패 주문을 표시하지 못한다.
- 관리자 상태는 저장된 주문 상태가 아니라 실패 시도의 존재 여부를 이용해 `결제실패`로 계산한다.
- 주문 생성 시 재고를 즉시 차감하며, 재고 부족 검사와 동일 상품 수량 합산 검사가 없다.
- 현재 테스트는 결제 응답의 `ok` 필드와 관리자 응답의 배열 여부만 확인하며 실패 상태·주문 보존·재고·관리자 실패 정보를 검증하지 않는다.

## Expected Behavior

- `pending` 주문의 결제가 실패하면 주문 상태를 `payment_failed`로 전환하고 주문과 실패 이력을 보존한다.
- 최초 결제 실패 요청에는 HTTP 402와 외부 노출에 안전한 실패 정보를 반환한다. 카드 정보, 내부 예외·메시지·스택과 원시 오류 응답은 노출하지 않는다.
- 결제 실패와 `payment_failed` 주문의 재결제 거부는 재고를 변경하지 않는다.
- `payment_failed` 주문은 같은 주문으로 다시 결제하거나 `pending`으로 되돌리지 않는다.
- 관리자 조회는 보존된 주문의 실제 `payment_failed` 상태를 사용하며, 실패 시도가 있다는 이유만으로 다른 상태를 덮어쓰지 않는다.
- 관리자에게 결제 실패 금액·시각·안전한 실패 사유를 조건부로 제공한다. 구체적인 제공 방식과 복수 실패 이력 선택 기준은 미정이다.

## Scope

- `payment_failed` 상태와 `pending`에서의 결제 실패 전환을 지원한다.
- 결제 실패 뒤 주문과 실패 결제 이력을 보존한다.
- 최초 결제 실패 응답을 HTTP 402로 변경하고 민감 정보와 내부 오류를 노출하지 않는다.
- 실패 결제와 동일 주문 재결제 거부 과정에서 주문 상태, 결제 이력과 재고를 정책에 맞게 보존한다.
- 관리자에게 실패 주문을 노출하려는 요청 의도는 포함한다. 기존 관리자 API 변경인지 새 UI까지 포함하는지는 미정이다.
- 재고 문제를 함께 다루려는 요청 의도는 포함한다. 적용할 재고 시나리오와 변경 범위는 미정이다.

## Out of Scope

- 실제 결제 제공자 또는 실거래 결제 연동
- 주문 취소와 환불 API 구현
- 네트워크·인프라 수준 결제 재시도 정책 확정
- 사람의 결정 전 새 관리자 UI, 결제 시점 재고 부족 처리와 환불 후 재고 복원을 구현 범위로 확정하는 것
- 목표 일정과 배포 범위를 근거 없이 확정하는 것

## Acceptance Criteria

- [ ] `pending` 주문에서 실패 결제를 수행하면 저장된 주문 상태가 `payment_failed`가 된다. 검증: 실패 결제 후 주문 저장 상태를 확인하는 테스트가 통과한다.
- [ ] 실패 결제 후 같은 주문 ID를 조회하면 주문이 삭제되지 않고 조회된다. 검증: 주문 조회 응답과 저장된 주문의 존재를 확인하는 테스트가 통과한다.
- [ ] 최초 결제 실패 요청은 HTTP 402를 반환한다. 검증: 결제 API 응답 상태를 확인하는 테스트가 통과한다.
- [ ] 실패 결제 시 주문 ID, 실패 결과, 금액과 시각을 가진 결제 시도가 보존된다. 검증: 결제 이력 저장 결과를 확인하는 테스트가 통과한다.
- [ ] 실패 응답과 관리자 조회에는 카드 정보, 내부 예외·메시지·스택과 원시 오류 응답이 포함되지 않는다. 검증: 응답 필드와 직렬화 결과를 확인하는 테스트가 통과한다.
- [ ] 결제 실패 전후의 재고 수량이 같다. 검증: 결제 직전과 실패 처리 후 상품 재고를 비교하는 테스트가 통과한다.
- [ ] `payment_failed` 주문에 다시 결제를 요청해도 상태가 바뀌지 않는다. 검증: 재결제 거부 뒤 주문 상태를 확인하는 테스트가 통과한다.
- [ ] `payment_failed` 주문의 재결제가 거부되어도 기존 결제 이력과 재고 수량이 바뀌지 않는다. 검증: 재결제 전후 저장 결과를 비교하는 테스트가 통과한다.

관리자 표시 방식과 안전한 실패 사유 형식이 결정되면 해당 결과를 독립적으로 판정하는 체크박스를 추가해야 한다.

## Human Decision Needed

- “관리자 화면”은 기존 `GET /admin/orders` API 변경을 뜻하는가, 별도 UI까지 포함하는가?
- 이번 작업에 포함할 재고 시나리오는 주문 생성 시 부족 검사, 결제 시점 재검사, 동일 상품 수량 합산과 중복 차감 방지 중 어디까지인가?
- 결제 실패 응답과 관리자 조회에 사용할 안전한 실패 사유의 필드명과 허용 값은 무엇인가?
- `payment_failed` 주문의 재결제 거부에 사용할 HTTP 상태와 응답 메시지는 무엇인가?
- 결제 시점에 재고가 부족할 때 주문 상태와 결제 응답은 무엇인가?
- 같은 주문에 실패 이력이 여러 개라면 관리자 조회에는 어느 이력을 표시하는가?
- 필수 테스트 범위, 목표 일정과 배포 범위는 무엇인가?
