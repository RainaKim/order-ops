## 현재 동작

| 케이스 | 시작 조건 | 현재 응답 | 처리 후 상태 | 주문 저장 여부 | 재고 변화 | 후속 조회 | 코드 근거 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 결제 성공 | `orders` Map에 존재하고 `status === "pending"`, `totalKrw > 0`인 주문. 카드 토큰은 비어 있지 않고 `FAIL`로 시작하지 않음 | 명시적 상태 지정 없이 `{ ok: true, order }` 반환. 기본 HTTP 상태는 200 | 저장된 주문 객체의 `status`가 `paid`로 변경됨 | 유지됨. 성공 분기에는 주문 삭제가 없음 | 결제 처리에서는 변화 없음. 주문 생성 시 이미 품목 수량만큼 감소함 | **단건 조회:** 기본 HTTP 200, `status: "paid"`.<br>**관리자 조회:** 해당 주문이 포함되고, 실패 결제 이력이 없으므로 표시 `status`는 `paid` | `src/payments.ts`, `src/orders.ts`, `src/admin.ts` |
| 결제 실패 | `orders` Map에 존재하는 결제 가능한 `pending` 주문. 카드 토큰이 `FAIL`로 시작함 | 명시적 상태 지정 없이 `{ ok: false }` 반환. 기본 HTTP 상태는 200 | 실패 분기에서 상태를 변경하지 않으므로 삭제 직전 주문 객체는 계속 `pending` | 유지되지 않음. 실패 시도 기록 후 `orders.delete(orderId)` 실행 | 결제 실패 처리에서는 변화나 복구 없음. 주문 생성 시 감소한 재고가 그대로 남음 | **단건 조회:** HTTP 404, `{ message: "Order not found" }`.<br>**관리자 조회:** 실패 시도 기록은 남지만 목록은 현재 `orders` Map으로 생성되므로 해당 주문은 포함되지 않음 | `src/payments.ts`, `src/orders.ts`, `src/admin.ts` |
| 재고 부족 주문 | 존재하는 한 상품에 대해 양의 정수 주문 수량 `Q`가 현재 재고 `S`보다 큼 | 재고량 검사 없이 `POST /orders`가 HTTP 201과 생성된 주문 반환 | 생성된 주문의 `status`는 `pending` | `orders` Map에 저장됨 | 재고가 `S - Q`로 감소하며 결과는 음수가 됨 | **단건 조회:** 기본 HTTP 200, `status: "pending"`.<br>**관리자 조회:** 해당 주문이 포함되고, 결제 시도가 없으므로 표시 `status`는 `pending` | `src/orders.ts`, `src/store.ts`, `src/admin.ts` |

## 수정 범위

| 사용자 동작 | 현재 동작과 확정된 변화 | 관련 파일과 책임 경계 | 완료 경계 |
| --- | --- | --- | --- |
| 주문 생성과 재고 부족 주문 차단 | 현재는 주문 생성 즉시 재고가 차감되고, 재고보다 많은 수량도 주문되어 재고가 음수가 됨. 확정 범위에서는 주문 생성 자체가 재고를 차감하지 않고, 재고가 부족한 주문은 저장과 재고 변경 전에 차단함 | `src/orders.ts`: 주문 생성·조회<br>`src/store.ts`: 주문과 상품 재고 저장 | 재고가 충분한 생성된 주문은 `pending`으로 저장되며 생성만으로 재고가 변하지 않음. 주문 수량이 현재 재고보다 많으면 주문은 저장되지 않고 재고도 변경되지 않음 |
| 결제 성공 | 현재는 주문 생성 때 이미 차감된 재고를 사용하고 결제 처리에서는 재고가 변하지 않음. 확정 범위에서는 결제 성공 시점에 재고를 차감함 | `src/payments.ts`: 결제 결과와 성공 처리<br>`src/store.ts`: 현재 재고와 주문 상태 저장 | 재고가 충분한 `pending` 주문만 `paid`가 되고, 해당 수량만큼 재고가 감소함 |
| 결제 실패 | 현재는 실패 시 주문을 삭제하고 기본 HTTP 200과 `{ ok: false }`를 반환함. 확정 범위에서는 주문을 `payment_failed`로 보존하고 HTTP 402와 실패 정보를 반환함 | `src/payments.ts`: 실패 처리와 API 응답<br>`src/store.ts`: `payment_failed` 상태와 실패 정보 저장<br>`src/orders.ts`: 보존된 주문 단건 조회 | 같은 주문이 `payment_failed` 상태로 남고, 단건 조회에서 HTTP 200으로 확인되며, 실패로 인해 재고가 감소하지 않음 |
| 실패 주문 재결제 | 현재는 주문이 삭제되어 재결제 대상이 없음. 확정 범위에서는 보존된 `payment_failed` 주문의 재결제를 허용하지 않음 | `src/payments.ts`: 후속 결제 요청 허용 여부<br>`src/store.ts`: 저장된 주문 상태 | 재결제 요청이 주문을 `paid`로 바꾸거나 재고를 차감하지 않음 |
| 관리자가 실패 주문 조회 | 현재는 실패 주문이 삭제되어 관리자 목록에 나타나지 않음. 확정 범위에서는 실패 주문을 상태·금액·시각·결제 실패 사유와 함께 표시함 | `src/admin.ts`: 관리자 응답 구성<br>`src/store.ts`: 주문과 실패 결제 정보 제공 | 해당 주문이 관리자 목록에 포함되고 실패 상태·금액·시각·결제 실패 사유가 확인됨 |

## 테스트·검증 계획

### 검증 시나리오

| 시나리오 | 준비 조건 | 행동 | 기대 결과 | 연결된 수정 범위 |
| --- | --- | --- | --- | --- |
| 충분한 재고의 주문 생성 | 상품 재고 `S`가 주문 수량 `Q` 이상임 | 수량 `Q`의 주문을 생성함 | 주문이 `pending`으로 저장되고, 생성 전후 재고는 `S`로 유지됨 | 주문 생성과 재고 부족 주문 차단 |
| 재고 부족 주문 차단 | 상품 재고 `S`보다 주문 수량 `Q`가 큼 | 수량 `Q`의 주문 생성을 시도함 | 주문이 저장되지 않고 재고는 `S`로 유지됨 | 주문 생성과 재고 부족 주문 차단 |
| 결제 성공 시 재고 차감 | 재고 `S ≥ Q`인 `pending` 주문이 있음 | 성공 가능한 결제를 요청함 | 주문이 `paid`가 되고 재고가 `S - Q`가 됨 | 결제 성공 |
| 결제 실패 주문 보존 | 재고 `S ≥ Q`인 `pending` 주문과 실패하도록 하는 결제 정보가 있음 | 결제를 요청함 | HTTP 402와 실패 정보가 반환됨. 주문은 `payment_failed`로 보존되고 단건 조회에서 HTTP 200으로 확인되며, 재고는 `S`로 유지됨 | 결제 실패 |
| 실패 주문 재결제 거부 | `payment_failed` 주문과 그 시점의 재고가 있음 | 같은 주문에 다시 결제를 요청함 | 주문 상태가 `paid`로 바뀌지 않고 재고도 감소하지 않음 | 실패 주문 재결제 |
| 관리자 실패 주문 조회 | `payment_failed` 주문과 실패 결제 기록이 저장되어 있음 | 관리자 주문 목록을 조회함 | 해당 주문이 목록에 포함되고 실패 상태·금액·시각·결제 실패 사유를 확인할 수 있음 | 관리자가 실패 주문 조회 |

재고 부족 요청의 HTTP 상태·응답 형식과 재결제 거부의 HTTP 상태·메시지는 확정된 정책이 아니므로 기대 결과에 포함하지 않는다. 환불·취소·라우팅·저장 기술 변경도 이 계획의 검증 대상이 아니다.

### 기존 검증 공백

검증 변경 대상은 `tests/orders.test.ts`다. 현재 주문 생성 테스트는 HTTP 201만, 단건 조회 테스트는 HTTP 200만, 결제 테스트는 응답의 `ok` 속성만, 관리자 조회 테스트는 응답이 배열인지만 확인한다. 따라서 재고 보존·차감 시점, 재고 부족 주문 미저장, `payment_failed` 주문 보존 및 조회, 재결제 후 상태·재고 불변, 관리자 목록의 실패 주문 상세 정보는 추가 검증이 필요하다.
