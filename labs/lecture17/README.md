# Lab 17 — 역할 분리: planner, implementer, reviewer

## 0. 이 랩이 끝나면

- planner, implementer, reviewer의 입력과 출력을 분리합니다.
- 같은 관리자 개선 작업을 역할 분리 workflow로 실행합니다.
- `docs/prompts/planner.md`, `implementer.md`, `reviewer.md`, `notes/role-split-run-l17.md`를 만듭니다.
- 예상 소요 시간은 45분입니다.

## 1. 시작 전 상태 확인

- 16강 PR preflight와 PR draft가 있어야 합니다.
- 실패 주문은 보존되지만 관리자 응답에 실패 사유 필드가 아직 없습니다.
- `deriveDisplayStatus()`의 기존 동작은 이번 강에서 수정하지 않습니다.

## 3. 실습

### E1. 역할 프롬프트 세 개 만들기

#### 설계 질문

- 각 역할이 받아야 할 입력과 넘겨야 할 출력은 무엇인가요?
- 역할이 자기 범위를 넘어가면 어디서 멈춰야 하나요?

#### 실행

세 파일에 역할 목적, 입력, 출력, 금지 조건, handoff 조건을 채우는 짧은 골격을 만듭니다.

#### 검증

- [ ] 세 역할 파일이 모두 있습니다.
- [ ] planner는 코드를 수정하지 않습니다.
- [ ] implementer는 승인된 plan 밖을 수정하지 않습니다.
- [ ] reviewer는 직접 수정보다 발견 사항 보고를 우선합니다.

### E2. 같은 작업 두 방식으로 실행하기

#### 설계 질문

- 관리자에게 실패 사유를 보여주려면 어떤 정책과 데이터가 필요한가요?
- 단일 세션과 역할 분리에서 계획 이탈과 검증 근거가 어떻게 달라지나요?

#### 실행

한 번은 단일 세션으로 계획만 만들고, 한 번은 세 역할을 순서대로 사용해 실패 사유 필드 노출을 구현합니다. 두 결과를 비교하되 `deriveDisplayStatus()`는 수정하지 않습니다.

#### 검증

- [ ] 관리자 응답에 정책에서 정한 실패 정보가 추가됩니다.
- [ ] 민감한 결제 토큰은 노출되지 않습니다.
- [ ] `deriveDisplayStatus()` diff가 없습니다.
- [ ] 두 방식의 변경 범위와 검증 결과가 기록됐습니다.

### E3. Reviewer 검토 실행하기

#### 설계 질문

- 구현이 plan과 다른 파일이나 필드를 건드렸나요?
- 실패 사유 필드에 대한 테스트와 개인정보 검토가 빠졌나요?

#### 실행

reviewer 프롬프트로 issue, plan, diff, tests를 대조하고 발견 사항을 `notes/role-split-run-l17.md`에 기록합니다. 필요한 테스트 보강은 별도 승인 뒤 수행합니다.

#### 검증

- [ ] 발견 사항에 파일과 근거가 있습니다.
- [ ] 계획 이탈과 테스트 누락이 별도 항목입니다.
- [ ] 수정 여부를 사람이 결정한 기록이 있습니다.

### E4. 사람 승인 지점 표시하기

#### 설계 질문

- 역할을 나눠도 자동화할 수 없는 정책과 위험 판단은 무엇인가요?
- 어떤 결과에서 구현 또는 리뷰를 중단해야 하나요?

#### 실행

실행 기록에 `## 사람 승인 지점`을 추가하고 역할 사이의 승인, 개인정보, 범위 변경, 테스트 실패 판단을 적은 뒤 검증하고 커밋합니다.

#### 검증

- [ ] 사람 승인 지점이 세 곳 이상 있습니다.
- [ ] 각 승인에 입력 자료와 가능한 결정이 있습니다.
- [ ] 전체 test, lint, typecheck가 통과합니다.
- [ ] 표시 상태의 기존 위험은 남아 있습니다.

## 5. 흔한 함정

- 역할 이름만 바꾸고 세 역할에 같은 요청을 줍니다.
- 실패 사유를 추가하면서 표시 상태 계산도 함께 고칩니다.
- reviewer가 발견 사항을 보고하지 않고 바로 코드를 수정합니다.
