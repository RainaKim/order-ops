# Lecture 01 transcript

## 요청 1: 프로젝트 설명 없음

사용자:

> 주문 상태 처리 개선해줘.

응답:

주문 상태는 문자열 대신 enum으로 정의하고 상태 전환을 한곳에서 관리하는 편이 좋습니다. 상태 머신 패턴을 적용하면 허용된 전환을 명시할 수 있고, 잘못된 전환은 예외로 처리할 수 있습니다. 서비스 계층에서 주문 조회, 상태 검증, 저장을 순서대로 수행하고 단위 테스트로 정상 전환과 잘못된 전환을 확인하세요.

검토 메모:

- 실제 repo 파일명은 언급되지 않았다.
- 현재 구현을 읽었다는 근거가 없다.
- 어떤 상태와 정책이 필요한지 확인하지 않았다.

## 요청 2: repo 맥락 제공

사용자:

> 주문 상태 처리 개선해줘.
>
> TypeScript와 Express를 사용한다. 주문은 `src/orders.ts`, 결제는 `src/payments.ts`, 관리자 조회는 `src/admin.ts`, in-memory 저장은 `src/store.ts`에 있다. 현재 상태는 pending, paid, cancelled뿐이다. 결제 실패 주문을 보존할지, 재고를 언제 줄일지, 관리자에게 무엇을 보여줄지는 아직 사람이 결정해야 한다. 먼저 현재 동작과 결정이 필요한 질문을 정리하고 코드는 수정하지 마.

응답:

현재 구조를 먼저 확인하겠습니다. `src/store.ts`의 상태 모델과 주문 저장 구조, `src/orders.ts`의 주문 생성 시 재고 변경, `src/payments.ts`의 실패 처리, `src/admin.ts`의 응답 필드를 읽어야 합니다. 구현 전에 다음 결정을 받아야 합니다.

1. 실패한 주문을 보존할지 삭제할지
2. 재고를 주문 생성 때 줄일지 결제 성공 때 줄일지
3. 관리자 응답에 결제 실패 정보를 어느 범위까지 노출할지

이 단계에서는 관련 파일과 현재 동작을 표로 정리하고, 결정이 끝날 때까지 코드 변경을 멈추겠습니다.

검토 메모:

- repo 파일을 직접 지목했다.
- 확인 전인 정책 세 가지를 질문으로 남겼다.
- 구현 전에 멈출 지점을 제안했다.
