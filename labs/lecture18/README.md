# Lab 18 — GitHub Issue 기반으로 작업 시작하기

## 0. 이 랩이 끝나면

- 프롬프트가 아니라 GitHub Issue를 작업의 시작점으로 사용합니다.
- VOC를 실제 Issue 한 건으로 등록하고 관련 문서, 코드, 테스트를 탐색합니다.
- `docs/prompts/issue-kickoff.md`를 만듭니다.
- 예상 소요 시간은 45분입니다.

## 1. 시작 전 상태 확인

- Lab 17 관리자 응답 변경과 역할 분리 기록이 있어야 합니다.
- `labs/fixtures/l18-voc-report.md`를 읽을 수 있어야 합니다.
- 생성한 독립 저장소에서 Issues 기능을 켜고, `origin`이 해당 저장소를 가리키는지 확인합니다.

## 2. 실습 목표와 산출물

| 단계 | 핵심 작업 | 결과 |
| --- | --- | --- |
| E1 | VOC와 기존 Issue 초안의 작업 가능성을 비교합니다. | 좋은 Issue와 나쁜 Issue의 차이 목록 |
| E2 | VOC를 생성한 독립 저장소의 GitHub Issue로 등록합니다. | Issues 탭의 신규 Issue |
| E3 | Issue에서 출발해 관련 문서·코드·테스트를 탐색합니다. | 근거 경로가 포함된 Issue 코멘트 |
| E4 | Issue URL부터 plan 승인까지 이어지는 prompt를 만듭니다. | `docs/prompts/issue-kickoff.md`와 완료 커밋 |

## 3. 실습

### E1. 좋은 Issue와 나쁜 Issue 비교하기

#### 설계 질문

- VOC 한 줄만으로 현재와 기대 동작을 구분할 수 있나요?
- 관련 정책, 재현 절차, 완료 기준 중 빠진 것은 무엇인가요?

#### 실행

VOC fixture와 Lab 08 Issue template을 대조하고 빠진 필드와 사람 결정 지점을 표시합니다. 코드는 수정하지 않습니다.

#### 검증

- [ ] 현재 동작과 기대 동작의 공백이 구분됐습니다.
- [ ] 재현에 필요한 입력과 관찰 대상이 적혔습니다.
- [ ] 구현 전에 확인할 정책이 연결됐습니다.

### E2. VOC를 GitHub Issue로 등록하기

#### 설계 질문

- 공개 Issue에 포함하면 안 되는 고객 정보가 있나요?
- 완료 기준이 증상을 다시 재현하고 해소 여부를 판정하나요?

#### 실행

생성한 저장소의 Issue template으로 VOC를 정리해 Issue 한 건을 등록합니다. 민감정보를 제거하고 아직 모르는 값은 미정으로 표시합니다.

#### 검증

- [ ] 개인 저장소 Issues 탭에 Issue가 한 건 있습니다.
- [ ] 재현 절차와 완료 기준이 있습니다.
- [ ] 민감한 결제 정보가 없습니다.
- [ ] Issue URL을 작업 메모에 남겼습니다.

### E3. Issue 기반 탐색하기

#### 설계 질문

- 표시 상태를 계산하는 함수와 결제 이력을 저장하는 위치는 어디인가요?
- 기존 테스트가 VOC 시나리오를 검증하나요?

#### 실행

Codex에게 Issue만 시작점으로 주고 관련 정책, 코드, 테스트를 찾게 합니다. 탐색 근거와 아직 확인할 내용을 Issue 코멘트로 남기고 구현은 멈춥니다.

#### 검증

- [ ] 코멘트에 관련 파일 경로가 있습니다.
- [ ] 현재 동작의 근거와 원인 가설이 구분됩니다.
- [ ] 아직 앱 코드 변경이 없습니다.

### E4. Issue kickoff 프롬프트 만들기

#### 설계 질문

- Issue에서 plan과 PR draft까지 넘길 최소 입력은 무엇인가요?
- 어떤 불확실성에서 사람에게 질문하고 멈춰야 하나요?

#### 실행

`docs/prompts/issue-kickoff.md`에 Issue URL, 읽을 기준, 탐색 결과, plan 경로, stop condition을 입력받는 빈칸 골격을 만들고 커밋합니다.

#### 검증

- [ ] Issue를 유일한 요청 원문으로 사용합니다.
- [ ] 구현 전 plan과 사람 승인을 요구합니다.
- [ ] PR draft까지의 handoff 위치가 있습니다.
- [ ] 이 lab의 커밋에 앱 코드 변경이 없습니다.

## 5. 흔한 함정

- 원본 template 저장소에 Issue를 등록해 실습 데이터가 외부 저장소에 남습니다.
- Issue 본문에 고객 식별 정보나 결제 토큰을 붙입니다.
- 탐색 코멘트를 남기기 전에 바로 표시 로직을 고칩니다.
