# Lab 01 — Codex를 써도 일이 안 줄어드는 4가지 패턴

## 0. 이 랩이 끝나면

- 설명이 사라짐, 정책을 임의로 정함, 검수 근거가 없음, 작업 자산이 남지 않음이라는 네 패턴을 구분합니다.
- 실습은 폐기할 별도 브랜치에서 진행하고 `main`의 앱 코드와 실습 산출물은 변경하지 않습니다.
- Lab 02 입력물인 `labs/fixtures/lecture01-transcript.md`의 위치를 확인합니다.
- 예상 소요 시간은 45분이며 실습은 선택입니다.

## 1. 시작 전 상태 확인

- `src/`와 `tests/`는 v0 상태입니다.
- root `AGENTS.md`, `docs/`, `notes/`, `.github/`는 아직 없습니다.
- 작업 트리에 변경이 없어야 합니다.
- 시작 상태가 다르면 현재 변경을 별도 브랜치에 보존한 뒤 새 독립 저장소에서 다시 시작합니다.

### 실습용 브랜치 준비

Lab 01의 재현 과정에서 Codex가 예상과 달리 코드를 수정할 수 있으므로 폐기할 브랜치를 먼저 만듭니다.

```bash
git status --short
git switch -c practice/lab01
```

`git status --short` 출력이 비어 있을 때만 브랜치를 만듭니다. 이 브랜치는 원격에 push하지 않으며 Lab 01이 끝나면 삭제합니다.

## 2. 실습 목표와 산출물

## 3. 실습

### E1. 선택 과제 — 패턴 1 재현하기

#### 설계 질문

- 세션 A에서 결정한 정책을 어떤 문장으로 명확하게 확정할까요?
- 세션 B가 같은 결정을 이어받았는지 무엇으로 판정할까요?

#### 실행

세션 A에서 repo 구조와 주문 상태 맥락을 제공하고 `주문 상태 처리 개선해줘`라고 요청합니다. 답변을 검토한 뒤 결제 실패 주문을 삭제하지 않고 보존한다는 결정을 명시적으로 남깁니다. 코드는 수정하지 않은 채 세션 A를 종료합니다.

완전히 새로운 세션 B에서 추가 맥락 없이 `어제 정한 대로 결제 실패 처리 이어서 해줘`라고 요청합니다. 세션 B가 앞선 결정을 되묻는지, 다른 정책을 가정하는지, 정확히 이어받는지를 관찰합니다.

#### 검증

- [ ] 세션 A에 결제 실패 주문의 보존 결정이 명시적으로 남았습니다.
- [ ] 세션 B는 세션 A의 대화 내용을 제공하지 않은 새 세션입니다.
- [ ] 세션 B가 앞선 결정을 이어받았는지 판정했습니다.
- [ ] 작업이 `practice/lab01` 브랜치 안에서 진행되고 있습니다.

### E2. 패턴 2 — 정책을 정하지 않고 바로 구현하기

#### 설계 질문

- 결제 실패 주문 보존, 재고 차감 시점, 관리자 노출 범위는 코드가 정할 문제인가요?
- 기준 문서가 없는 상태에서 구현을 밀어붙이면 어떤 선택이 코드에 섞일까요?

#### 실행

`결제 실패 상태 처리해줘`라는 요청에 대한 응답을 관찰합니다. 구현을 시작하기 전에 질문하는지 확인하고, 바로 구현하거나 `알아서 진행해줘`라는 후속 요청 뒤 변경안을 제시하면 다음 세 정책을 어떻게 정했는지 찾습니다. 실제 변경은 적용하거나 커밋하지 않습니다.

1. 실패한 주문을 보존할지 삭제할지
2. 재고를 언제 차감하거나 차단할지
3. 관리자 응답에 실패 정보를 어디까지 노출할지

#### 검증

- [ ] 구현 전에 정책 질문이 있었는지 확인했습니다.
- [ ] 답변에서 세 정책에 해당하는 선택을 찾았습니다.
- [ ] 선택의 근거가 repo에 존재하는지 구분했습니다.
- [ ] 앱 코드와 테스트 변경을 남기지 않았습니다.

### E3. 패턴 3 — 검수할 근거가 없는 답변 확인하기

#### 설계 질문

- 답변만 보고 변경 대상과 현재 동작을 확인할 수 있나요?
- 실행한 검증 명령과 결과가 없을 때 완료 여부를 판단할 수 있나요?

#### 실행

E2에서 확인한 마지막 답변을 다시 읽고 다음 네 항목을 표시합니다.

1. 어느 파일을 변경하는가
2. 무엇을 근거로 현재 동작을 판단했는가
3. 어떤 검증 명령을 실행했는가
4. 검증 결과가 무엇인가

없는 항목을 다시 확인하기 위해 직접 코드를 탐색하거나 테스트를 실행해야 한다면, 그 작업도 검수 비용으로 봅니다.

#### 검증

- [ ] 네 항목의 존재 여부를 각각 판정했습니다.
- [ ] 답변의 주장과 실행 근거를 구분했습니다.
- [ ] 추가 확인이 필요한 항목을 찾았습니다.
- [ ] 검수 가능한 답변에 필요한 정보를 설명할 수 있습니다.

### E4. 패턴 4 — 대화가 작업 자산으로 남았는지 확인하기

#### 설계 질문

- 대화가 끝난 뒤 다음 작업이 읽을 수 있는 파일은 무엇인가요?
- 좋은 결정과 분석이 대화창에만 있으면 어디에서 다시 설명해야 하나요?

#### 실행

다음 위치에 E1~E3에서 나온 결정, 근거, 다음 작업이 남아 있는지 확인합니다. 없는 위치를 이 Lab에서 미리 만들지는 않습니다.

1. 생성한 독립 저장소의 GitHub Issues
2. `docs/`
3. root `AGENTS.md`
4. 코드의 TODO
5. 생성한 독립 저장소의 Pull Requests

#### 검증

- [ ] 다섯 위치의 현재 상태를 확인했습니다.
- [ ] 대화에서 나온 내용과 repo에 남은 자산을 구분했습니다.
- [ ] 다음 세션이 대화 없이 읽을 수 있는 결정 기록이 없음을 확인했습니다.
- [ ] 빈 위치를 Lab 01에서 미리 채우지 않았습니다.

### 실습용 브랜치 정리

먼저 실습 중 생긴 변경을 확인합니다.

```bash
git status --short
```

출력이 있다면 변경을 실습 브랜치에만 임시 커밋합니다. 미커밋 변경을 남긴 채 `main`으로 이동하면 변경이 함께 따라올 수 있습니다.

```bash
git add -A
git commit -m "chore: preserve Lab 01 experiment"
```

변경이 없다면 위 커밋 단계는 건너뜁니다. 그다음 `main`으로 돌아와 실습 브랜치를 삭제합니다.

```bash
git switch main
git branch -D practice/lab01
git status --short
```

마지막 `git status --short` 출력이 비어 있어야 합니다. `practice/lab01`을 이미 원격에 push했다면 원격 브랜치는 자동으로 삭제되지 않으므로 먼저 현재 저장소에서 해당 브랜치를 확인합니다.
