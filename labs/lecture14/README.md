# Lab 14 — 테스트 보강: 의미 있는 assertion 만들기

## 0. 이 랩이 끝나면

- 핵심 상태 변화 세 가지를 테스트 대상으로 고릅니다.
- `tests/payments.test.ts`, `tests/admin.test.ts`를 만들고 기존 assertion을 강화합니다.
- `notes/assertion-review-l14.md`에 red-green 과정과 assertion 비교를 남깁니다.
- 예상 소요 시간은 45분입니다.

## 1. 시작 전 상태 확인

- Lab 13 종료 상태에서 `src/`는 Lab 12와 같아야 합니다.
- 기존 `tests/orders.test.ts`는 얕은 assertion 네 개를 갖고 있어야 합니다.
- 현재 테스트와 정책 문서 세 개를 먼저 읽습니다.

## 2. 실습 목표와 산출물

| 단계 | 핵심 작업 | 결과 |
| --- | --- | --- |
| E1 | 위험과 관찰값을 기준으로 핵심 테스트 세 개를 고릅니다. | `notes/assertion-review-l14.md` 초안 |
| E2 | 결제 상태와 실패 주문 보존을 red-green으로 검증합니다. | `tests/payments.test.ts`와 실행 기록 |
| E3 | 관리자 상태와 재고 변화 assertion을 강화합니다. | `tests/admin.test.ts`, 강화된 `tests/orders.test.ts` |
| E4 | 약한 assertion과 의미 있는 assertion을 비교합니다. | 완성된 assertion review와 완료 커밋 |

## 3. 실습

### E1. 핵심 케이스 세 개 고르기

#### 설계 질문

- 정책상 위험하지만 기존 테스트가 보지 않는 상태 변화는 무엇인가요?
- 응답 코드보다 더 중요한 저장 상태와 재고 값은 무엇인가요?

#### 실행

세 핵심 케이스, 실패 시 위험, 관찰할 값을 `notes/assertion-review-l14.md`에 기록합니다. 아직 테스트 코드는 쓰지 않습니다.

#### 검증

- [ ] 세 케이스가 서로 다른 정책을 검증합니다.
- [ ] 각 케이스에 관찰할 구체 값이 있습니다.
- [ ] 기존 테스트가 놓치는 이유가 기록됐습니다.

### E2. Red-green 흐름 확인하기

#### 설계 질문

- 새 테스트가 처음 실패해야 변경 가치를 증명할 수 있나요?
- 실패 이유가 환경 문제가 아니라 assertion 대상 때문인가요?

#### 실행

`tests/payments.test.ts`에 결제 상태와 실패 주문 보존을 검증하는 테스트를 추가합니다. 실패 결과를 기록한 뒤 Lab 12 구현과 맞는지 확인하고 green 결과를 남깁니다.

#### 검증

- [ ] red 상태의 명령과 실패 이유가 기록됐습니다.
- [ ] green 상태에서 같은 테스트가 통과합니다.
- [ ] HTTP 응답뿐 아니라 저장 상태를 검증합니다.

### E3. 상태와 재고 assertion 강화하기

#### 설계 질문

- 관리자 응답에서 반드시 보여야 할 상태는 무엇인가요?
- 주문과 결제 전후 재고 숫자를 직접 비교할 수 있나요?

#### 실행

`tests/admin.test.ts`를 만들고 `tests/orders.test.ts`의 얕은 assertion을 상태, 응답 필드, 재고 변화 중심으로 교정합니다. `src/`는 수정하지 않습니다.

#### 검증

- [ ] tests 파일이 세 개입니다.
- [ ] 성공 결제 전후 재고 값을 검증합니다.
- [ ] 실패 주문의 보존 상태를 검증합니다.
- [ ] `src/` diff가 없습니다.

### E4. Assertion 비교 기록 완성하기

#### 설계 질문

- 통과해도 회귀를 잡지 못하는 assertion은 무엇인가요?
- 강화된 assertion이 어떤 정책을 보호하나요?

#### 실행

assertion review에 기존 검사, 강화 검사, 잡아내는 회귀를 비교하고 전체 검증 결과를 기록한 뒤 커밋합니다.

#### 검증

- [ ] 비교 표가 세 행 이상입니다.
- [ ] 각 강화 assertion이 정책 문서를 참조합니다.
- [ ] 전체 테스트, lint, typecheck가 통과합니다.
- [ ] 이 lab의 커밋에 src 변경이 없습니다.

## 5. 자주 하는 실수

- red와 green 사이에 무엇이 달라졌는지 기록하지 않습니다.
