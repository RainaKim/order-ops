## 3. 실습

### E1. 관련 파일 후보 찾기

이번 단계에서는 수정할 파일을 바로 확정하지 않습니다. 요청이 들어오는 지점에서 상태 저장소와 테스트까지 실제 연결을 따라가며, 이후 단계에서 다시 확인할 후보를 만듭니다. Lab 04에서 작성한 root `AGENTS.md`가 새 Task에 자동으로 적용되고, `Before Editing`의 읽기 순서와 계획 우선 기준이 실제 탐색으로 이어지는 첫 단계입니다.

#### 이번 단계의 범위

| 구분 | 내용 |
| --- | --- |
| 하는 것 | 관련 파일을 탐색하고 역할에 따라 후보를 분류합니다. |
| 하지 않는 것 | 정책 결정, 수정 범위 확정, 코드와 테스트 변경은 하지 않습니다. |
| 종료 상태 | `notes/order-status-plan.md`의 `## 관련 파일 후보`만 완성합니다. |

#### 진행 흐름

```mermaid
flowchart LR
    Mention["@로 요청 파일 연결"] --> Explore["Plan mode에서 영향 경로 탐색"]
    Explore --> Classify["후보 역할 분류"]
    Classify --> Review["사람이 후보 범위 확인"]
    Review --> Record["관련 파일 후보 기록"]
```

#### 설계 질문

- 요청 기록은 직접 문맥으로 연결하되, 관련 소스까지 미리 지정하지 않고 Codex가 찾게 할 수 있나요?
- 요청 진입점에서 상태 저장소와 테스트까지 어떤 연결을 따라가야 하나요?
- 관련 파일과 실제 수정 후보를 구분할 수 있나요?

#### 실행

새 Task에서 요청 기록을 mention하고 Plan mode로 탐색을 시작합니다. 이때 소스 파일을 미리 지정하지 않고, Codex가 `AGENTS.md`의 `Before Editing`에 따라 요청 진입점에서 상태 저장소와 테스트까지 연결을 찾게 합니다.

첫 대화에서는 파일 후보마다 현재 역할, 요청과 연결되는 이유, 근거 위치를 제시하게 합니다. 결과를 바로 기록하지 말고, 주문 생성·결제 처리·주문 조회·관리자 조회·기존 테스트가 하나의 흐름으로 이어지는지 먼저 읽습니다.

이후 같은 Task에서 후보를 다음 역할로 다시 분류하게 합니다.

- 기능 수정 후보: 요청의 동작을 소유하는 코드
- 검증 변경 후보: 변경 후 동작을 검증할 테스트
- 탐색 전용: 연결과 라우팅을 이해하기 위한 코드
- 검사 범위 근거: 구현 후 사용할 명령과 검사 범위를 확인하는 설정

후보가 누락되거나 너무 넓다면, 파일명을 답으로 주기보다 빠진 역할이나 과도한 분류를 지적해 다시 탐색하게 합니다.

```
목표: 결제 실패 상태 개선에 필요한 관련 파일 후보와 선택 이유를 찾는다
문맥: mention으로 연결한 요청 기록, 자동 로드된 root AGENTS.md, repo의 실제 연결
제약: 읽기만 하고 정책·수정 내용을 확정하거나 파일을 수정하지 않는다
완료 조건: 후보마다 repo 상대 경로·현재 역할·요청 연결 이유·근거 위치가 있다
```

```
목표: 방금 찾은 후보를 기능 수정 후보·검증 변경 후보·탐색 전용·검사 범위 근거로 분류한다
문맥: 직전 후보 표와 각 파일의 실제 import·router·test 연결
제약: 새 정책·구체적 변경 방법을 만들지 않고 분류 이유를 함께 적는다
완료 조건: 모든 후보에 분류와 유지·제외 이유가 있고 누락 가능성이 보고되어 있다
```

```
목표: 확인된 후보를 notes/order-status-plan.md의 ## 관련 파일 후보에 기록한다
문맥: 이 Task에서 검토하고 승인한 후보와 분류만 사용한다
제약: repo 상대 경로와 선택 이유만 쓰고 정책·수정안은 쓰지 않으며 src와 tests는 수정하지 않는다
완료 조건: 모든 경로가 존재하고 후보마다 분류와 이유가 있으며 다른 파일 변경이 없다
```

##### 사람 확인 — 후보 범위

다음 항목을 확인한 뒤에만 기록 단계로 넘어갑니다.

- 상태 타입과 주문·상품·결제 기록의 저장 위치가 포함됐는가?
- 주문 생성, 결제 처리, 주문 조회, 관리자 조회가 끊김 없이 연결됐는가?
- 기존 테스트가 검증 변경 후보로 포함됐는가?
- 앱 조립 파일과 검사 설정을 기능 수정 대상으로 오해하지 않았는가?
- 정책 선택이나 구체적인 수정 방법이 후보 이유에 섞이지 않았는가?

누락이 있으면 어떤 역할이 빠졌는지만 알려 다시 탐색하게 합니다. 사람이 파일명을 대신 채워 주지는 않습니다.

##### 기록

후보 범위를 확인한 뒤에만 `notes/order-status-plan.md`의 `## 관련 파일 후보`에 기록합니다. 계획 문서에는 repo 상대 경로, 역할, 선택 이유, 분류만 남깁니다. 채팅에서 확인한 절대 경로와 라인 번호는 탐색 근거로만 쓰고 복사하지 않습니다.

##### 왜 이 순서인가

탐색 결과를 즉시 파일에 저장하면 관련성만 있는 파일과 실제 변경 가능성이 있는 파일이 섞입니다. 영향 경로를 먼저 확인하고 사람이 후보 범위를 검토한 뒤 기록하면, E2에서는 확정된 탐색 범위를 다시 찾지 않고 현재 동작 확인에 집중할 수 있습니다.

##### 이 단계에서 자주 나오는 실수

- 요청에 적힌 단어와 파일 이름만 비교하고 import와 라우터 연결을 따라가지 않습니다.
- 관련 파일을 모두 수정 대상으로 분류합니다.
- 채팅에 표시된 절대 경로와 라인 번호를 계획 문서에 그대로 복사합니다.
- 후보를 찾는 동안 원하는 상태나 응답을 이미 구현 방법처럼 적습니다.

#### 검증

- [ ] 후보 파일이 세 개 이상 있습니다.
- [ ] 각 후보에 선택 이유가 있습니다.
- [ ] 후보가 기능 수정, 검증 변경, 탐색 전용, 검사 범위 근거로 구분됐습니다.
- [ ] 파일 경로가 repo 상대 경로로 적혀 있고 실제로 존재합니다.
- [ ] `notes/order-status-plan.md` 외의 파일과 `src/`, `tests/`에 변경이 없습니다.

### E2. 현재 동작 표 만들기

E1에서 관련 파일 후보를 찾았다면, 이제 같은 파일을 다시 나열하는 대신 세 가지 케이스가 코드 안에서 어떻게 흘러가는지 확인합니다. 이 단계의 표는 이후 수정안을 쓰기 위한 출발점입니다. 현재 코드와 원하는 정책을 섞으면 E3의 수정 범위와 E4의 검증 기준도 함께 흔들리므로, 응답·상태·저장·재고를 서로 다른 사실로 기록합니다.

#### 이번 단계의 범위

| 구분 | 내용 |
| --- | --- |
| 하는 것 | 결제 성공·결제 실패·재고 부족 주문의 현재 응답, 주문 상태, 저장 여부, 재고 변화를 코드에서 확인합니다. |
| 하지 않는 것 | 원하는 동작 작성, 정책 선택, 수정 범위 확정, 테스트 설계, 코드와 테스트 변경은 하지 않습니다. |
| 종료 상태 | `notes/order-status-plan.md`의 `## 현재 동작` 표만 완성합니다. |

#### 진행 흐름

```mermaid
flowchart LR
    Candidates["E1 관련 파일 후보"] --> Trace["세 케이스의 코드 경로 추적"]
    Trace --> Separate["응답·상태·저장·재고 분리"]
    Separate --> Review["사람이 현재 사실 확인"]
    Review --> Record["현재 동작 표 기록"]
```

#### 설계 질문

- 각 케이스는 어떤 요청에서 시작해 어떤 응답과 저장 결과로 끝나나요?
- 주문 상태의 변화와 주문이 저장소에 남아 있는지는 어떻게 구분할 수 있나요?
- 주문 상태와 재고 변화가 서로 다른 시점에 일어나는지 확인했나요?

#### 실행

같은 Task에서 E1의 관련 파일 후보를 출발점으로 삼아 결제 성공, 결제 실패, 재고 부족 주문을 각각 추적합니다. 주문 생성부터 시작해 결제 또는 재고 조건을 지나고, 후속 주문 조회와 관리자 조회까지 연결을 따라갑니다.

이번 단계에서는 앱을 실행하지 않으므로 코드에서 확인한 동작과 실행해서 관찰한 결과를 구분합니다. 요청 기록은 어떤 동작을 개선하려는지 이해하는 문맥으로 사용하고, `## 현재 동작`의 직접 근거는 현재 `src/`와 `tests/`에서 찾습니다.

##### 현재 동작을 읽는 기준

| 관점 | 확인할 질문 |
| --- | --- |
| 시작 조건 | 어떤 주문과 입력으로 케이스가 시작되는가? |
| 현재 응답 | 현재 코드는 어떤 HTTP 상태와 본문을 반환하는가? |
| 주문 상태 | 처리 전후에 `Order.status`가 어떻게 달라지는가? |
| 저장 여부 | 처리 후 주문이 `orders` 저장소에 남아 있는가? |
| 재고 변화 | 재고는 어느 시점에 어떤 방향으로 변하는가? |
| 후속 조회 | 같은 주문의 단건 조회와 관리자 조회는 무엇을 읽는가? |
| 코드 근거 | 이 판단을 뒷받침하는 파일과 처리 지점은 어디인가? |

세 케이스에는 같은 관점을 적용합니다.

- 결제 성공: 주문 생성부터 성공 결제와 후속 조회까지 추적합니다.
- 결제 실패: 주문 생성부터 실패 분기와 후속 조회까지 추적합니다.
- 재고 부족: 보유 재고보다 많은 수량을 요청했을 때의 주문 생성 경로를 추적합니다.

##### 사람 확인 — 현재 사실과 기대 분리

다음 항목을 확인한 뒤에만 기록 단계로 넘어갑니다.

- HTTP 응답과 저장소에 남은 결과가 별도 열로 구분됐는가?
- 처리 전 상태, 처리 후 상태, 주문 저장 여부를 추정 없이 기록했는가?
- 주문 상태와 재고 변화를 하나의 결과처럼 섞지 않았는가?
- 요청 문서의 원하는 상태·응답·처리 방침이 현재 동작에 들어가지 않았는가?
- 기존 테스트가 확인하지 않는 흐름을 테스트로 검증됐다고 표현하지 않았는가?
- 각 행의 근거가 E1에서 찾은 실제 처리 파일과 연결되는가?

사실이 불분명하면 기대값을 채우지 말고, 어떤 관점의 근거가 부족한지 알려 해당 코드 경로를 다시 확인하게 합니다.

##### 기록

현재 사실을 확인한 뒤 `notes/order-status-plan.md`에 `## 현재 동작`을 추가합니다. 기존 `## 관련 파일 후보`는 보존하고, 승인한 세 케이스의 표만 기록합니다. 정책 결정, 수정 범위, 테스트 계획은 다음 단계의 입력이므로 아직 작성하지 않습니다.

##### 왜 이 순서인가

같은 API 응답이라도 주문이 저장소에 남는지, 상태가 바뀌는지, 재고가 변하는지는 서로 다를 수 있습니다. 이를 먼저 분리해 두면 E3에서 현재 코드와 사람이 선택한 정책의 차이만 수정 범위로 옮길 수 있습니다.

##### 이 단계에서 자주 나오는 실수

- 요청 문서의 원하는 상태를 현재 코드의 상태처럼 적습니다.
- HTTP 성공 응답을 주문 처리 성공과 같은 의미로 해석합니다.
- 주문이 남아 있는지 확인하지 않고 처리 후 상태를 추정합니다.
- 재고 부족을 주문 상태처럼 기록하거나 재고 검사 여부를 확인하지 않습니다.
- 기존 테스트 파일이 있다는 이유만으로 세 케이스가 이미 검증됐다고 판단합니다.

#### 검증

- [ ] 표에 세 케이스가 있습니다.
- [ ] 각 행에 현재 응답, 처리 후 상태, 주문 저장 여부, 재고 변화가 구분돼 있습니다.
- [ ] 각 행에 현재 코드의 근거 파일과 처리 지점이 있습니다.
- [ ] 원하는 정책과 수정 제안을 현재 동작 표에 섞지 않았습니다.
- [ ] 기존 `## 관련 파일 후보`와 `src/`, `tests/`가 변경되지 않았습니다.

### E3. 수정 범위와 제외 범위 나누기

E1과 E2에서는 관련 파일과 현재 동작을 사실로 확인했습니다. 이제 Codex가 정책을 추측하게 두지 않고, 사람이 이번 요청에 필요한 결정을 내린 뒤 그 결과를 구현 전 작업 경계로 바꿉니다. 이때 수정 범위는 사람의 결정뿐 아니라 E2에서 확인한 현재 결함도 함께 반영합니다.

#### 이번 단계의 범위

| 구분 | 내용 |
| --- | --- |
| 하는 것 | 미결 정책의 영향을 확인하고, 사람이 이번 요청에 필요한 결정을 내린 뒤 수정 범위와 제외 범위를 정합니다. |
| 하지 않는 것 | 관련 파일 재탐색, 현재 동작 재작성, 구현 방법 확정, 테스트 케이스 작성, 코드와 테스트 변경은 하지 않습니다. |
| 종료 상태 | `notes/order-status-plan.md`의 `## 수정 범위`와 `## 제외 범위`만 완성합니다. |

#### 진행 흐름

```mermaid
flowchart LR
    Questions["미결 정책과 영향 회수"] --> Decide["사람이 필요한 정책 결정"]
    Decide --> Scope["결정과 현재 결함을 범위로 변환"]
    Scope --> Review["사람이 작업 경계 확인"]
    Review --> Record["수정·제외 범위 기록"]
```

#### 설계 질문

- 이번 요청의 수정 범위를 정하려면 어떤 정책에 사람의 답이 필요한가요?
- E2에서 확인한 현재 문제 중 정책 선택과 별개로 수정 범위에서 판단할 결함은 무엇인가요?
- 요청을 완료하려면 미룰 수 없는 변화와, 지금 포함하면 범위가 커지는 작업은 무엇인가요?
- 사람이 미룬 정책과 현재 구조를 유지하는 경계를 어떻게 구분할 수 있나요?

#### 실행

같은 Task에서 `notes/pending-decisions.md`, `notes/task-boundary.md`, `notes/order-status-request.md`, `notes/order-status-plan.md`를 연결합니다. E1의 관련 파일 후보와 E2의 현재 동작은 다시 조사하지 않고, 이번 요청의 범위를 정할 때 영향을 주는 미결 정책만 정리하게 합니다.

첫 결과에서는 Codex가 답을 선택하거나 수정 범위를 확정해서는 안 됩니다. 각 질문이 현재 동작의 어느 부분과 연결되는지, 선택에 따라 기존 관련 파일의 책임이 어떻게 달라지는지, 이번에 미룰 수 있는지를 사람이 비교할 수 있어야 합니다.

##### 결정 자료를 읽는 기준

| 관점 | 확인할 질문 |
| --- | --- |
| 미결 정책 | 아직 사람이 선택하지 않은 질문은 무엇인가? |
| 현재 동작 | 각 선택이 E2의 어느 케이스와 연결되는가? |
| 파일 영향 | E1에서 확인한 기존 후보 중 어느 파일의 책임이 달라지는가? |
| 지금 결정할 이유 | 답이 없으면 이번 수정 범위를 확정할 수 없는가? |
| 미룰 수 있는 이유 | 이번 요청을 완료하는 데 필요하지 않은 후속 동작인가? |
| 추가 결정 | E2에서 확인했지만 기존 질문에 포함되지 않은 문제가 있는가? |

##### 사람 결정 — 이번 요청에 필요한 만큼

결정 자료를 확인한 뒤 사람이 이번 요청에 필요한 정책을 선택합니다. 모든 도메인 정책을 한 번에 완성하지 않습니다. 지금 답해야 하는 질문에는 방침을 남기고, 후속 작업으로 분리할 질문에는 이번에 다루지 않는다고 명시합니다.

결정을 남길 때는 다음 세 종류를 구분합니다.

- 이번 요청에서 확정할 정책: 원하는 상태·저장·조회 동작을 정합니다.
- 이번 작업에서 미룰 정책: 현재 동작을 유지할지, 후속 결정으로 넘길지 명시합니다.
- 유지할 구조: 현재 저장 방식과 API 경계처럼 이번 요청에서 바꾸지 않을 구조를 한정합니다.

이 결정은 이번 작업의 계획에만 적용됩니다. 장기간 반복해서 적용할 도메인 기준으로 승격하는 작업은 이후 lab에서 다룹니다.

##### 결정과 현재 결함을 작업 범위로 바꾸기

사람의 결정이 끝나면, Codex에게 결정 결과와 `## 현재 동작`에서 확인한 결함을 함께 수정 범위와 제외 범위로 정리하게 합니다. 사람의 결정만 옮기고 E2의 문제를 빠뜨리거나, 반대로 현재 동작 표의 모든 문제를 자동으로 수정 범위에 넣어서는 안 됩니다.

범위의 근거는 다음처럼 구분합니다.

| 구분 | 범위에서의 처리 |
| --- | --- |
| 사람이 확정한 정책 | 현재 동작과의 차이를 수정 범위에 연결합니다. |
| 확인된 현재 결함 | 요청과 문서화된 기준에 연결되는지 판단해 수정 범위에 반영합니다. |
| 사람이 미룬 정책 | 답을 보완하지 않고 제외 범위에 남깁니다. |
| 유지할 구조 | 새로운 확장 작업을 상상하지 않고 현재 경계로 기록합니다. |

같은 사용자 동작이 여러 파일에 걸쳐 있더라도 파일마다 별도 작업으로 반복하지 않습니다. 변경할 동작을 먼저 묶고, E1에서 확인한 관련 파일과 각 파일이 책임질 경계를 연결합니다. 테스트 파일은 독립적인 기능 범위로 부풀리지 않고 관련 변경의 검증 책임으로만 표시하며, 구체적인 테스트 계획은 E4로 넘깁니다.

##### 범위 제안이 갖춰야 할 정보

| 구분 | 포함할 정보 |
| --- | --- |
| 수정 범위 | 확정된 변화, 현재 동작과의 차이, 관련 파일, 완료 경계 |
| 제외 범위 | 미룬 정책 또는 유지할 구조, 미루는 이유, 현재 유지할 동작 |

##### 사람 확인 — 결정과 작업 경계

다음 항목을 확인한 뒤에만 기록 단계로 넘어갑니다.

- 사람이 선택한 정책이 빠짐없이 수정 범위에 반영됐는가?
- E2에서 확인한 각 케이스가 포함 또는 제외 판단을 받았는가?
- 같은 사용자 동작이 파일별 작업으로 중복되지 않았는가?
- 사람이 미룬 정책을 Codex가 임의로 보완하지 않았는가?
- 바꾸지 않을 파일과 이번 작업에서 제외할 동작이 구분됐는가?
- 현재 구현과 관계없는 제외 작업을 새로 상상하지 않았는가?
- 구현 순서와 구체적인 테스트 케이스가 미리 들어가지 않았는가?

결정이 누락됐다면 사람이 방침을 추가하고, 범위 번역이 잘못됐다면 빠진 현재 동작이나 과도하게 확장된 경계만 지적해 다시 정리하게 합니다. Codex에게 정책 선택을 돌려보내지 않습니다.

```

문맥: @notes/pending-decisions.md @notes/task-boundary.md @notes/order-status-request.md @notes/order-status-plan.md
제약: 후보·현재 동작을 다시 조사하거나 답·수정·제외 판단을 대신 정하지 않고 파일을 수정하지 않는다
완료 조건: 지금 결정할 질문과 나중에 미룰 질문을 판단할 수 있는 자료를 채팅에 제시한다
```

```

문맥: 사람의 결정과 order-status-plan.md의 ## 관련 파일 후보·## 현재 동작
제약: 새 파일 탐색·후보 재분류·미룬 정책 보완·구현 방법·테스트 케이스 작성·파일 수정을 하지 않는다
완료 조건: 수정 범위에는 변화·현재와의 차이·관련 파일·완료 경계, 제외 범위에는 이유·유지 동작이 있다
```

제약: 기존 후보·현재 동작을 보존하고 수정·제외 범위만 추가하며 다른 파일은 수정하지 않는다
완료 조건: 수정·제외 범위의 각 항목에 필요한 경계와 이유가 있다

구현 방법이나 테스트 계획의 선행 작성을 확인해라. 파일은 수정하지 말고 결과만 보고해줘.

##### 기록

작업 경계를 확인한 뒤 `notes/order-status-plan.md`에 `## 수정 범위`와 `## 제외 범위`를 추가합니다. 기존 `## 관련 파일 후보`와 `## 현재 동작`은 보존합니다. 승인한 정책과 현재 결함의 범위만 기록하고, 사람이 미룬 결정의 답이나 E4의 테스트 계획은 추가하지 않습니다.

##### 왜 이 순서인가

정책 결정 전에 범위를 작성하면 Codex가 미결 질문의 답을 대신 선택하거나 모든 선택지를 계획에 넣게 됩니다. 반대로 사람의 결정만 옮기면 E2에서 발견한 현재 결함이 빠질 수 있습니다. 결정 자료를 먼저 확인하고 사람이 선택한 뒤, 그 선택과 현재 결함을 함께 범위로 바꾸면 수정 이유와 제외 이유를 모두 추적할 수 있습니다.

##### 이 단계에서 자주 나오는 실수

- Codex가 미결 정책의 추천안을 그대로 확정하게 둡니다.
- E1의 파일 후보를 다시 찾거나 모든 후보를 수정 대상으로 재분류합니다.
- 현재 결함을 모두 자동으로 포함하거나, 사람의 결정만 반영하고 현재 결함을 빠뜨립니다.
- 테스트 변경을 별도 기능 범위로 만들고 E4의 테스트 케이스까지 작성합니다.
- 프로젝트에서 가능한 모든 확장을 상상해 제외 범위를 불필요하게 늘립니다.

#### 검증

- [ ] 수정 범위마다 확정된 변화, 현재 동작과의 차이, 관련 파일, 완료 경계가 있습니다.
- [ ] E2의 현재 결함이 범위 판단에 반영됐습니다.
- [ ] 제외 범위마다 미룬 이유와 현재 유지할 동작이 있습니다.
- [ ] 사람이 미룬 정책이 임의로 확정되지 않았습니다.
- [ ] 관련 파일 후보를 다시 분류하거나 구체적인 테스트 계획을 작성하지 않았습니다.
- [ ] `notes/order-status-plan.md` 외의 파일과 `src/`, `tests/`에 변경이 없습니다.

### E4. 구현 직전에서 멈추기

E3에서 무엇을 바꾸고 무엇을 미룰지 정했다면, 마지막으로 각 범위를 구현 후 판정할 수 있는 결과로 바꿉니다. 이 단계에서는 테스트를 작성하거나 검증 명령을 실행하지 않습니다. 어떤 동작을 어떤 근거로 확인하고, 어느 실패에서 완료 판단을 멈출지만 계획합니다.

#### 이번 단계의 범위

| 구분 | 내용 |
| --- | --- |
| 하는 것 | 수정 범위를 검증 시나리오로 바꾸고, 기존 테스트의 공백과 구현 후 실행할 검증 명령·판정 기준을 정합니다. |
| 하지 않는 것 | 테스트 코드 작성, 앱 코드 변경, 검증 명령 실행, 미결 정책의 기대값 확정은 하지 않습니다. |
| 종료 상태 | `notes/order-status-plan.md`의 `## 테스트·검증 계획`을 완성하고 구현 직전에서 멈춥니다. |

#### 설계 질문

- E3의 각 수정 범위는 어떤 준비·행동·결과로 관찰할 수 있나요?
- 현재 테스트가 확인하는 것과 구현 후 추가로 확인할 것은 무엇인가요?
- 명령이 성공했다는 사실과 필요한 시나리오가 모두 검증됐다는 사실을 구분했나요?
- 어떤 검증 실패에서 완료 판단과 최종 보고를 멈춰야 하나요?

#### 실행

같은 Task에서 `notes/order-status-plan.md`의 `## 수정 범위`, `## 제외 범위`, `## 현재 동작`을 연결합니다. 먼저 수정 범위마다 구현 후 참이어야 할 결과를 준비 조건·행동·관찰 결과로 나눠 채팅에 정리하게 합니다. 제외 범위와 사람이 확정하지 않은 응답 계약은 기대 결과에 넣지 않습니다.

##### 시나리오를 읽는 기준

| 관점 | 확인할 질문 |
| --- | --- |
| 준비 조건 | 어떤 주문 상태, 재고, 입력이 먼저 필요한가? |
| 행동 | 어느 주문·결제·조회 요청을 수행하는가? |
| 관찰 결과 | 응답, 주문 상태, 저장 여부, 재고, 조회 결과 중 무엇을 판정하는가? |
| 범위 연결 | E3의 어느 수정 범위를 검증하는가? |
| 정책 경계 | 사람이 미룬 응답 형식이나 후속 동작을 기대값으로 만들지 않았는가? |

검증 흐름은 결제 성공, 결제 실패, 재고 부족 주문, 관리자 실패 사유 조회를 구분해 확인합니다. 하나의 흐름을 여러 테스트로 나눌 수 있지만, 다른 테스트의 실행 결과가 있어야만 시작할 수 있게 만들지는 않습니다. 저장 여부와 재고처럼 API 응답만으로 보이지 않는 결과는 기존 저장 상태의 전후 비교가 필요한 관찰 대상으로 표시합니다.

시나리오를 작성하면서 E3의 수정·제외 범위와 기대 결과가 충돌한다면 테스트 계획에서 원하는 결과만 바꾸지 않습니다. E3의 사람 결정과 작업 경계를 먼저 정정한 뒤, 정정된 범위에서 시나리오를 다시 도출합니다. 이미 일치한다면 되돌아갈 필요가 없습니다.

##### 기존 테스트와 검증 공백 대조

시나리오를 확인한 뒤 기존 `tests/orders.test.ts`와 대조합니다. 각 흐름에서 현재 assertion이 실제로 확인하는 것과 추가로 검증해야 하는 결과를 분리합니다. 테스트 파일이 존재하거나 엔드포인트를 호출한다는 사실만으로 해당 동작이 검증된다고 판단하지 않습니다.

| 검증 흐름 | 현재 테스트가 확인하는 것 | 추가로 확인할 결과 | 검증 변경 파일 |
| --- | --- | --- | --- |
| 결제 성공 |  |  |  |
| 결제 실패 |  |  |  |
| 재고 부족 주문 |  |  |  |
| 관리자 실패 사유 |  |  |  |

여기서는 검증 공백과 기존 파일의 책임만 정합니다. 테스트 이름, assertion 코드, fixture 구성 같은 구현 상세는 작성하지 않습니다.

##### 명령과 판정 기준 연결

기존 테스트와 공백을 확인한 다음 `AGENTS.md`의 `Commands`와 `package.json`의 scripts를 대조해 구현 후 실행 계획을 만듭니다. 이번 완료 판단에 사용하는 명령은 `npm test`, `npm run lint`, `npm run typecheck`입니다. 서버를 계속 실행하는 개발·실행 명령은 이번 자동 검증 계획에 추가하지 않습니다.

| 명령 | 확인할 내용 |
| --- | --- |
| `npm test` | 시나리오별 대응 테스트가 마련됐는지 먼저 대조하고, 실행된 테스트가 모두 통과하는지 확인합니다. |
| `npm run lint` | `src`와 `tests`의 정적 규칙 위반 여부를 확인합니다. |
| `npm run typecheck` | 변경된 소스와 테스트의 타입 일관성을 확인합니다. |

각 명령에는 검증 목적, 실행 시점, 통과 기준, 실패 시 멈출 조건을 적습니다. 테스트 명령의 성공만으로 필요한 테스트가 모두 존재한다고 판단하지 않습니다. 시나리오와 테스트의 대응은 실행 전에 확인하고, 명령 결과는 실제 실행된 검증의 성공 여부로 판정합니다.

##### 구현 직전에서 멈추기

계획을 기록한 뒤 `git diff --stat -- src/ tests/`로 구현 파일과 테스트가 바뀌지 않았는지 확인합니다. 출력이 없어야 합니다. 계획 문서만 커밋하고, 애플리케이션 검증 명령은 구현 후 실행할 계획으로 남긴 채 이번 lab을 종료합니다.

##### 왜 이 순서인가

수정 범위를 바로 테스트 이름으로 옮기면 준비 조건과 실제 관찰 결과가 빠질 수 있습니다. 먼저 사용자 흐름을 판정 가능한 결과로 만들고 기존 테스트의 공백을 확인한 뒤 명령에 연결하면, 테스트가 통과해도 필요한 동작이 검증되지 않는 상황을 줄일 수 있습니다.

- 사람이 미룬 응답 코드나 필드 값을 테스트 기대값으로 확정합니다.

- `npm test`가 성공하면 필요한 테스트가 모두 존재한다고 판단합니다.
- 계획을 작성하다가 테스트 코드나 앱 코드를 먼저 수정합니다.
