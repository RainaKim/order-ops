- `notes/order-status-plan.md`를 완성합니다.
- 앱 코드와 테스트는 한 줄도 변경하지 않은 상태를 유지합니다.

## 3. 실습

### E1. 관련 파일 후보 찾기

이번 단계에서는 수정할 파일을 바로 확정하지 않습니다. 요청이 들어오는 지점에서 상태 저장소와 테스트까지 실제 연결을 따라가며, 이후 단계에서 다시 확인할 후보를 만듭니다. Lab 04에서 작성한 root `AGENTS.md`가 새 Task에 자동으로 적용되고, `Before Editing`의 읽기 순서와 계획 우선 기준이 실제 탐색으로 이어지는 첫 단계입니다.

#### 이번 단계의 범위

| 구분 | 내용 |
| --- | --- |
| 하는 것 | 관련 파일을 탐색하고 역할에 따라 후보를 분류합니다. |
| 하지 않는 것 | 정책 결정, 수정 범위 확정, 코드와 테스트 변경은 하지 않습니다. |
| 종료 상태 | `notes/order-status-plan.md`의 `## 관련 파일 후보`만 완성합니다. |

#### 진행 흐름

```mermaid
flowchart LR
    Mention["@로 요청 파일 연결"] --> Explore["Plan mode에서 영향 경로 탐색"]
    Explore --> Classify["후보 역할 분류"]
    Classify --> Review["사람이 후보 범위 확인"]
    Review --> Record["관련 파일 후보 기록"]
```

#### 설계 질문

- 요청 기록은 직접 문맥으로 연결하되, 관련 소스까지 미리 지정하지 않고 Codex가 찾게 할 수 있나요?
- 요청 진입점에서 상태 저장소와 테스트까지 어떤 연결을 따라가야 하나요?
- 관련 파일과 실제 수정 후보를 구분할 수 있나요?

#### 실행

새 Task에서 요청 기록을 mention하고 Plan mode로 탐색을 시작합니다. 이때 소스 파일을 미리 지정하지 않고, Codex가 `AGENTS.md`의 `Before Editing`에 따라 요청 진입점에서 상태 저장소와 테스트까지 연결을 찾게 합니다.

첫 대화에서는 파일 후보마다 현재 역할, 요청과 연결되는 이유, 근거 위치를 제시하게 합니다. 결과를 바로 기록하지 말고, 주문 생성·결제 처리·주문 조회·관리자 조회·기존 테스트가 하나의 흐름으로 이어지는지 먼저 읽습니다.

이후 같은 Task에서 후보를 다음 역할로 다시 분류하게 합니다.

- 기능 수정 후보: 요청의 동작을 소유하는 코드
- 검증 변경 후보: 변경 후 동작을 검증할 테스트
- 탐색 전용: 연결과 라우팅을 이해하기 위한 코드
- 검사 범위 근거: 구현 후 사용할 명령과 검사 범위를 확인하는 설정

후보가 누락되거나 너무 넓다면, 파일명을 답으로 주기보다 빠진 역할이나 과도한 분류를 지적해 다시 탐색하게 합니다.

##### 사람 확인 — 후보 범위

다음 항목을 확인한 뒤에만 기록 단계로 넘어갑니다.

- 상태 타입과 주문·상품·결제 기록의 저장 위치가 포함됐는가?
- 주문 생성, 결제 처리, 주문 조회, 관리자 조회가 끊김 없이 연결됐는가?
- 기존 테스트가 검증 변경 후보로 포함됐는가?
- 앱 조립 파일과 검사 설정을 기능 수정 대상으로 오해하지 않았는가?
- 정책 선택이나 구체적인 수정 방법이 후보 이유에 섞이지 않았는가?

누락이 있으면 어떤 역할이 빠졌는지만 알려 다시 탐색하게 합니다. 사람이 파일명을 대신 채워 주지는 않습니다.

##### 기록

후보 범위를 확인한 뒤에만 `notes/order-status-plan.md`의 `## 관련 파일 후보`에 기록합니다. 계획 문서에는 repo 상대 경로, 역할, 선택 이유, 분류만 남깁니다. 채팅에서 확인한 절대 경로와 라인 번호는 탐색 근거로만 쓰고 복사하지 않습니다.

##### 왜 이 순서인가

탐색 결과를 즉시 파일에 저장하면 관련성만 있는 파일과 실제 변경 가능성이 있는 파일이 섞입니다. 영향 경로를 먼저 확인하고 사람이 후보 범위를 검토한 뒤 기록하면, E2에서는 확정된 탐색 범위를 다시 찾지 않고 현재 동작 확인에 집중할 수 있습니다.

##### 이 단계에서 자주 나오는 실수

- 요청에 적힌 단어와 파일 이름만 비교하고 import와 라우터 연결을 따라가지 않습니다.
- 관련 파일을 모두 수정 대상으로 분류합니다.
- 채팅에 표시된 절대 경로와 라인 번호를 계획 문서에 그대로 복사합니다.
- 후보를 찾는 동안 원하는 상태나 응답을 이미 구현 방법처럼 적습니다.

#### 검증

- [ ] 후보 파일이 세 개 이상 있습니다.
- [ ] 각 후보에 선택 이유가 있습니다.
- [ ] 후보가 기능 수정, 검증 변경, 탐색 전용, 검사 범위 근거로 구분됐습니다.
- [ ] 파일 경로가 repo 상대 경로로 적혀 있고 실제로 존재합니다.
- [ ] `notes/order-status-plan.md` 외의 파일과 `src/`, `tests/`에 변경이 없습니다.

### E2. 현재 동작 표 만들기

E1에서 관련 파일 후보를 찾았다면, 이제 같은 파일을 다시 나열하는 대신 세 가지 케이스가 코드 안에서 어떻게 흘러가는지 확인합니다. 이 단계의 표는 이후 수정안을 쓰기 위한 출발점입니다. 현재 코드와 원하는 정책을 섞으면 E3의 수정 범위와 E4의 검증 기준도 함께 흔들리므로, 응답·상태·저장·재고를 서로 다른 사실로 기록합니다.

#### 이번 단계의 범위

| 구분 | 내용 |
| --- | --- |
| 하는 것 | 결제 성공·결제 실패·재고 부족 주문의 현재 응답, 주문 상태, 저장 여부, 재고 변화를 코드에서 확인합니다. |
| 하지 않는 것 | 원하는 동작 작성, 정책 선택, 수정 범위 확정, 테스트 설계, 코드와 테스트 변경은 하지 않습니다. |
| 종료 상태 | `notes/order-status-plan.md`의 `## 현재 동작` 표만 완성합니다. |

#### 진행 흐름

```mermaid
flowchart LR
    Candidates["E1 관련 파일 후보"] --> Trace["세 케이스의 코드 경로 추적"]
    Trace --> Separate["응답·상태·저장·재고 분리"]
    Separate --> Review["사람이 현재 사실 확인"]
    Review --> Record["현재 동작 표 기록"]
```

#### 설계 질문

- 각 케이스는 어떤 요청에서 시작해 어떤 응답과 저장 결과로 끝나나요?
- 주문 상태의 변화와 주문이 저장소에 남아 있는지는 어떻게 구분할 수 있나요?
- 주문 상태와 재고 변화가 서로 다른 시점에 일어나는지 확인했나요?

#### 실행

같은 Task에서 E1의 관련 파일 후보를 출발점으로 삼아 결제 성공, 결제 실패, 재고 부족 주문을 각각 추적합니다. 주문 생성부터 시작해 결제 또는 재고 조건을 지나고, 후속 주문 조회와 관리자 조회까지 연결을 따라갑니다.

이번 단계에서는 앱을 실행하지 않으므로 코드에서 확인한 동작과 실행해서 관찰한 결과를 구분합니다. 요청 기록은 어떤 동작을 개선하려는지 이해하는 문맥으로 사용하고, `## 현재 동작`의 직접 근거는 현재 `src/`와 `tests/`에서 찾습니다.

##### 현재 동작을 읽는 기준

| 관점 | 확인할 질문 |
| --- | --- |
| 시작 조건 | 어떤 주문과 입력으로 케이스가 시작되는가? |
| 현재 응답 | 현재 코드는 어떤 HTTP 상태와 본문을 반환하는가? |
| 주문 상태 | 처리 전후에 `Order.status`가 어떻게 달라지는가? |
| 저장 여부 | 처리 후 주문이 `orders` 저장소에 남아 있는가? |
| 재고 변화 | 재고는 어느 시점에 어떤 방향으로 변하는가? |
| 후속 조회 | 같은 주문의 단건 조회와 관리자 조회는 무엇을 읽는가? |
| 코드 근거 | 이 판단을 뒷받침하는 파일과 처리 지점은 어디인가? |

세 케이스에는 같은 관점을 적용합니다.

- 결제 성공: 주문 생성부터 성공 결제와 후속 조회까지 추적합니다.
- 결제 실패: 주문 생성부터 실패 분기와 후속 조회까지 추적합니다.
- 재고 부족: 보유 재고보다 많은 수량을 요청했을 때의 주문 생성 경로를 추적합니다.

##### 표가 갖춰야 할 정보

| 케이스 | 시작 조건 | 현재 응답 | 처리 후 주문 상태 | 주문 저장 여부 | 재고 변화 | 후속 조회 | 코드 근거 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 결제 성공 |  |  |  |  |  |  |  |
| 결제 실패 |  |  |  |  |  |  |  |
| 재고 부족 |  |  |  |  |  |  |  |

Codex가 처음 만든 표를 바로 계획 문서에 옮기지 않습니다. 각 행이 실제 처리 경로와 연결되는지 먼저 확인합니다. 채팅에서는 파일과 라인 번호로 근거를 검토할 수 있지만, 계획 문서에는 repo 상대 경로와 코드의 역할을 남깁니다.

##### 사람 확인 — 현재 사실과 기대 분리

다음 항목을 확인한 뒤에만 기록 단계로 넘어갑니다.

- HTTP 응답과 저장소에 남은 결과가 별도 열로 구분됐는가?
- 처리 전 상태, 처리 후 상태, 주문 저장 여부를 추정 없이 기록했는가?
- 주문 상태와 재고 변화를 하나의 결과처럼 섞지 않았는가?
- 요청 문서의 원하는 상태·응답·처리 방침이 현재 동작에 들어가지 않았는가?
- 기존 테스트가 확인하지 않는 흐름을 테스트로 검증됐다고 표현하지 않았는가?
- 각 행의 근거가 E1에서 찾은 실제 처리 파일과 연결되는가?

사실이 불분명하면 기대값을 채우지 말고, 어떤 관점의 근거가 부족한지 알려 해당 코드 경로를 다시 확인하게 합니다.

##### 기록

현재 사실을 확인한 뒤 `notes/order-status-plan.md`에 `## 현재 동작`을 추가합니다. 기존 `## 관련 파일 후보`는 보존하고, 승인한 세 케이스의 표만 기록합니다. 정책 결정, 수정 범위, 테스트 계획은 다음 단계의 입력이므로 아직 작성하지 않습니다.

##### 왜 이 순서인가

같은 API 응답이라도 주문이 저장소에 남는지, 상태가 바뀌는지, 재고가 변하는지는 서로 다를 수 있습니다. 이를 먼저 분리해 두면 E3에서 현재 코드와 사람이 선택한 정책의 차이만 수정 범위로 옮길 수 있습니다.

##### 이 단계에서 자주 나오는 실수

- 요청 문서의 원하는 상태를 현재 코드의 상태처럼 적습니다.
- HTTP 성공 응답을 주문 처리 성공과 같은 의미로 해석합니다.
- 주문이 남아 있는지 확인하지 않고 처리 후 상태를 추정합니다.
- 재고 부족을 주문 상태처럼 기록하거나 재고 검사 여부를 확인하지 않습니다.
- 기존 테스트 파일이 있다는 이유만으로 세 케이스가 이미 검증됐다고 판단합니다.

#### 검증

- [ ] 표에 세 케이스가 있습니다.
- [ ] 각 행에 현재 응답, 처리 후 상태, 주문 저장 여부, 재고 변화가 구분돼 있습니다.
- [ ] 각 행에 현재 코드의 근거 파일과 처리 지점이 있습니다.
- [ ] 원하는 정책과 수정 제안을 현재 동작 표에 섞지 않았습니다.
- [ ] 기존 `## 관련 파일 후보`와 `src/`, `tests/`가 변경되지 않았습니다.

### E4. 구현 직전에서 멈추기

#### 설계 질문

- 변경 후 참이어야 할 테스트 케이스는 무엇인가요?
- 어떤 검증 실패에서 구현을 중단해야 하나요?

#### 실행

`## 테스트·검증 계획`에 네 케이스와 실행 명령을 적고 plan만 커밋합니다.
