## 3. 실습

### E1. 관련 파일 후보 찾기

이번 단계에서는 수정할 파일을 바로 확정하지 않습니다. 요청이 들어오는 지점에서 상태 저장소와 테스트까지 실제 연결을 따라가며, 이후 단계에서 다시 확인할 후보를 만듭니다. Lab 04에서 작성한 root `AGENTS.md`가 새 Task에 자동으로 적용되고, `Before Editing`의 읽기 순서와 계획 우선 기준이 실제 탐색으로 이어지는 첫 단계입니다.

#### 이번 단계의 범위

| 구분 | 내용 |
| --- | --- |
| 하는 것 | 관련 파일을 탐색하고 역할에 따라 후보를 분류합니다. |
| 하지 않는 것 | 정책 결정, 수정 범위 확정, 코드와 테스트 변경은 하지 않습니다. |
| 종료 상태 | `notes/order-status-plan.md`의 `## 관련 파일 후보`만 완성합니다. |

#### 진행 흐름

```mermaid
flowchart LR
    Mention["@로 요청 파일 연결"] --> Explore["Plan mode에서 영향 경로 탐색"]
    Explore --> Classify["후보 역할 분류"]
    Classify --> Review["사람이 후보 범위 확인"]
    Review --> Record["관련 파일 후보 기록"]
```

#### 설계 질문

- 요청 기록은 직접 문맥으로 연결하되, 관련 소스까지 미리 지정하지 않고 Codex가 찾게 할 수 있나요?
- 요청 진입점에서 상태 저장소와 테스트까지 어떤 연결을 따라가야 하나요?
- 관련 파일과 실제 수정 후보를 구분할 수 있나요?

#### 실행

##### 1. 새 Task에 입력 파일 연결하기

`order-ops`에서 새 Task를 열어 root `AGENTS.md`가 자동으로 적용되는 상태로 시작합니다. 입력창에서 `@`를 입력하고 나타나는 검색 목록에서 `notes/order-status-request.md`를 선택합니다. 선택된 파일이 입력창에 연결된 것을 확인합니다. Markdown 링크를 직접 타이핑하는 것은 mention이 아닙니다.

이 단계에서는 요청 기록만 mention합니다. `src/`와 `tests/`의 관련 파일은 Codex가 `AGENTS.md`의 `Before Editing`에 따라 직접 찾게 둡니다.

##### 2. Plan mode에서 영향 경로 탐색하기

`/plan` 또는 `Shift+Tab`으로 Plan mode를 켜고 다음 계약을 보냅니다.

```text
목표: 결제 실패 상태 개선에 필요한 관련 파일 후보와 선택 이유를 찾는다
문맥: mention으로 연결한 요청 기록, 자동 로드된 root AGENTS.md, repo에서 확인되는 실제 연결
제약: 읽기만 하고 정책·수정 내용을 확정하거나 어떤 파일도 수정하지 않는다
완료 조건: 후보마다 repo 상대 경로·현재 역할·요청과 연결되는 이유·근거 위치가 있다
```

Codex가 반환한 후보를 바로 계획 문서에 옮기지 않습니다. 먼저 요청 진입점, 상태와 저장 구조, 성공·실패 처리, 결과를 소비하는 조회, 기존 테스트까지 연결이 이어지는지 확인합니다. 근거 위치는 채팅에서 파일과 라인으로 확인할 수 있지만, 계획 문서에는 코드가 움직여도 의미가 유지되는 경로와 역할을 남깁니다.

##### 3. 후보 역할 분류하기

첫 결과에 누락이나 과잉 후보가 있으면 같은 Task에서 피드백합니다. 후보가 충분하면 다음 계약으로 역할을 분류합니다.

```text
목표: 방금 찾은 후보를 기능 수정 후보·검증 변경 후보·탐색 전용·검사 범위 근거로 분류한다
문맥: 직전 후보 표와 각 파일의 실제 import·router·test 연결
제약: 새 정책이나 구체적인 변경 방법을 만들지 않고 분류 이유를 함께 적는다
완료 조건: 모든 후보에 분류와 유지·제외 이유가 있고 누락 가능성이 보고되어 있다
```

##### 사람 확인 — 후보 범위

다음 항목을 확인한 뒤에만 기록 단계로 넘어갑니다.

- 상태 타입과 주문·상품·결제 기록의 저장 위치가 포함됐는가?
- 주문 생성, 결제 처리, 주문 조회, 관리자 조회가 끊김 없이 연결됐는가?
- 기존 테스트가 검증 변경 후보로 포함됐는가?
- 앱 조립 파일과 검사 설정을 기능 수정 대상으로 오해하지 않았는가?
- 정책 선택이나 구체적인 수정 방법이 후보 이유에 섞이지 않았는가?

누락이 있으면 어떤 역할이 빠졌는지만 알려 다시 탐색하게 합니다. 사람이 파일명을 대신 채워 주지는 않습니다.

##### 4. 확인된 후보만 계획 문서에 기록하기

후보 범위를 확인한 뒤 Default mode로 돌아와 다음 계약을 보냅니다.

```text
목표: 확인된 후보를 notes/order-status-plan.md의 ## 관련 파일 후보에 기록한다
문맥: 이 Task에서 검토하고 승인한 후보와 분류만 사용한다
제약: repo 상대 경로와 선택 이유만 쓰고 정책·수정안은 쓰지 않으며 src와 tests는 수정하지 않는다
완료 조건: 모든 경로가 존재하고 후보마다 분류와 이유가 있으며 다른 파일 변경이 없다
```

##### 왜 이 순서인가

탐색 결과를 즉시 파일에 저장하면 관련성만 있는 파일과 실제 변경 가능성이 있는 파일이 섞입니다. 영향 경로를 먼저 확인하고 사람이 후보 범위를 검토한 뒤 기록하면, E2에서는 확정된 탐색 범위를 다시 찾지 않고 현재 동작 확인에 집중할 수 있습니다.

##### 이 단계에서 자주 나오는 실수

- 요청에 적힌 단어와 파일 이름만 비교하고 import와 라우터 연결을 따라가지 않습니다.
- 관련 파일을 모두 수정 대상으로 분류합니다.
- 채팅에 표시된 절대 경로와 라인 번호를 계획 문서에 그대로 복사합니다.
- 후보를 찾는 동안 원하는 상태나 응답을 이미 구현 방법처럼 적습니다.

#### 검증

- [ ] 후보 파일이 세 개 이상 있습니다.
- [ ] 각 후보에 선택 이유가 있습니다.
- [ ] 후보가 기능 수정, 검증 변경, 탐색 전용, 검사 범위 근거로 구분됐습니다.
- [ ] 파일 경로가 repo 상대 경로로 적혀 있고 실제로 존재합니다.
- [ ] `notes/order-status-plan.md` 외의 파일과 `src/`, `tests/`에 변경이 없습니다.

### E2. 현재 동작 표 만들기

#### 설계 질문

#### 검증

- [ ] 기대 동작을 현재 동작 칸에 섞지 않았습니다.

#### 실행
