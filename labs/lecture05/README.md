# Lab 05 — 작은 요청 하나를 plan-first로 통과시키기

## 0. 이 랩이 끝나면

- 관련 파일, 현재 동작, 수정 범위, 제외 범위, 검증 계획을 구현 전에 정리합니다.
- `notes/order-status-plan.md`를 완성합니다.
- 앱 코드와 테스트는 한 줄도 변경하지 않은 상태를 유지합니다.
- 예상 소요 시간은 45분입니다.

## 1. 시작 전 상태 확인

- root `AGENTS.md`가 다섯 섹션을 갖춰야 합니다.
- `labs/fixtures/l05-current-behavior-observed.md`를 읽을 수 있어야 합니다.
- `src/`, `tests/`는 v0이며 작업 트리에 변경이 없어야 합니다.

## 2. 실습 목표와 산출물

| 단계 | 핵심 작업 | 결과 |
| --- | --- | --- |
| E1 | 관련 파일 후보와 선택 근거를 찾습니다. | `notes/order-status-plan.md`의 관련 파일 후보 |
| E2 | 결제 성공·실패와 재고 부족의 현재 동작을 기록합니다. | 같은 파일의 현재 동작 표 |
| E3 | 수정 범위와 제외 범위를 분리합니다. | 같은 파일의 범위 정의 |
| E4 | 테스트와 검증 계획을 정하고 구현 전에 멈춥니다. | 완성된 plan과 완료 커밋 |

## 3. 실습

### E1. 관련 파일 후보 찾기

#### 설계 질문

- 요청 경로를 조립하는 파일과 상태를 저장하는 파일은 무엇인가요?
- 후보 파일마다 읽어야 하는 이유를 설명할 수 있나요?

#### 실행

`notes/order-status-plan.md`에 `## 관련 파일 후보`를 만들고 파일 경로와 선택 이유를 기록합니다. 수정은 시작하지 않습니다.

#### 검증

- [ ] 후보 파일이 세 개 이상 있습니다.
- [ ] 각 후보에 선택 이유가 있습니다.
- [ ] 파일 경로가 실제로 존재합니다.

### E2. 현재 동작 표 만들기

#### 설계 질문

- 결제 성공, 결제 실패, 재고 부족 주문에서 실제 응답과 저장 상태는 무엇인가요?
- 관찰 결과와 기대 정책을 분리했나요?

#### 실행

fixture와 현재 코드를 근거로 `## 현재 동작` 표를 작성합니다. 세 케이스의 요청, 응답, 주문 상태, 재고 영향을 기록합니다.

#### 검증

- [ ] 표에 세 케이스가 있습니다.
- [ ] 각 행에 관찰 근거가 있습니다.
- [ ] 기대 동작을 현재 동작 칸에 섞지 않았습니다.

### E3. 수정 범위와 제외 범위 나누기

#### 설계 질문

- 요청을 충족하는 최소 변경은 무엇인가요?
- 이번 작업에서 미루지 않으면 범위가 커지는 항목은 무엇인가요?

#### 실행

`## 수정 범위`와 `## 제외 범위`를 만들고 각 항목의 경계와 이유를 적습니다.

#### 검증

- [ ] 수정 범위가 세 항목 이하입니다.
- [ ] 제외 범위가 세 항목 이상 있습니다.
- [ ] 정책 결정이 필요한 항목은 별도 표시했습니다.

### E4. 구현 직전에서 멈추기

#### 설계 질문

- 변경 후 참이어야 할 테스트 케이스는 무엇인가요?
- 어떤 검증 실패에서 구현을 중단해야 하나요?

#### 실행

`## 테스트·검증 계획`에 네 케이스와 실행 명령을 적고 plan만 커밋합니다.

#### 검증

- [ ] 테스트 케이스가 네 개 이상 있습니다.
- [ ] `npm test`, `npm run lint`, `npm run typecheck`가 계획에 있습니다.
- [ ] `git diff --stat -- src/ tests/` 결과가 비어 있습니다.
- [ ] 커밋에 notes 파일만 포함됐습니다.

## 5. 자주 하는 실수

- 계획을 세우는 중에 작은 수정이라며 코드를 먼저 바꿉니다.
