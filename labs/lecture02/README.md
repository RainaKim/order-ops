# Lab 02 — 대화창 답변을 작업 자산으로 바꾸기

## 0. 이 랩이 끝나면

- 세션이 바뀌어도 유지해야 할 요청과 맥락을 대화 로그에서 추출합니다.
- 확인된 사실, 추정, 사람의 결정을 구분하고 다음 세션의 시작점을 파일로 남깁니다.
- `notes/order-status-request.md`, `notes/pending-decisions.md`, `notes/next-actions.md`를 만듭니다.
- 예상 소요 시간은 45분입니다.

## 1. 시작 전 상태 확인

- `labs/fixtures/lecture01-transcript.md`가 존재해야 합니다.
- `notes/`는 아직 없고 `src/`, `tests/`는 v0입니다.
- 시작 상태가 다르면 현재 변경을 별도 브랜치에 보존한 뒤 새 독립 저장소에서 다시 시작합니다.

## 2. 실습 목표와 산출물

| 단계 | 핵심 작업 | 결과 |
| --- | --- | --- |
| E1 | 세션별 요청에서 다음 작업에도 필요한 맥락을 추출합니다. | `notes/order-status-request.md`의 요청 원문 |
| E2 | 코드와 테스트를 근거로 사실, 추정, 대화 속 결정을 구분합니다. | 같은 파일의 확인된 사실과 추정 |
| E3 | 대화에서 결정된 것처럼 보이는 정책과 미결정 질문을 다시 확인합니다. | `notes/pending-decisions.md` |
| E4 | 다음 세션이 바로 시작할 수 있는 정보를 남깁니다. | `notes/next-actions.md`와 완료 커밋 |

## 3. 실습

### E1. 세션을 넘어갈 맥락 추출하기

#### 설계 질문

- 세션이 바뀌어도 유지되어야 하는 요청과 제약은 무엇인가요?
- 다음 세션이 다시 읽어야 할 문장과 그렇지 않은 문장을 가를 수 있나요?

#### 실행

transcript의 세션별 요청과 응답을 읽고 다음 작업에서도 필요한 요청 원문과 제약을 문장 단위로 추출합니다. 줄글을 통째로 옮기지 않고, 다음 세션에 옮겨 적을 문장만 남깁니다. E1에서는 코드를 열지 않습니다.

```
목표: transcript를 notes/order-status-request.md 로 옮긴다
      문장을 다듬거나 요약하지 않고, 세 소제목으로 나눠 담는다
문맥: labs/fixtures/lecture01-transcript.md
      사용자가 쓴 컨텍스트·요청·완료 조건과 agent 답변 3개가 들어 있다
제약: ## 요청 원문 — 사용자가 쓴 것. 요청 문장, 완료 조건, 지켜야 할 정책
      ## repo를 짚은 문장 — 지금 코드가 어떻다고 서술한 문장. 제안이 아니라 현재 상태
      ## 짚은 데 없는 문장 — 코드가 그렇다고 확인할 수 없는 문장. 제안·단정·요청에 없던 것
      repo 소개 첫 문단과 세션 B 응답만 빼고, 나머지는 모두 어딘가에 담는다
      사실인지 추정인지는 아직 가르지 않는다 · src/와 tests/는 열지 않는다
완료 조건: 세 소제목이 모두 있고, 완료 조건 네 줄이 원문 그대로 남아 있다
```

#### 검증

- [ ] `notes/order-status-request.md`에 `## 요청 원문`이 있습니다.
- [ ] 요청 원문의 의미를 바꾸지 않았습니다.
- [ ] 세션이 바뀌면 사라질 수 있는 맥락을 요청 원문과 함께 남겼습니다.
- [ ] 줄글을 통째로 복사하지 않고 다음 세션에 옮겨 적을 문장만 남겼습니다.

### E2. 사실, 추정, 대화 속 결정 구분하기

#### 설계 질문

- 파일이나 실행 결과로 확인된 문장은 무엇인가요?
- 답변의 추정과 대화에서 결정된 것처럼 보이는 정책은 어떻게 구분할까요?

#### 실행

`src/`, `tests/`를 읽어 transcript의 주장을 확인합니다. `order-status-request.md`에 `## 확인된 사실`과 `## 추정`을 나누고 사실에는 근거 파일을 붙입니다. 대화에서 나온 정책은 코드의 현재 동작과 섞지 말고 별도로 표시합니다.

```
목표: E1이 만든 ## repo를 짚은 문장과 ## 짚은 데 없는 문장을
      코드로 대조해 ## 확인된 사실과 ## 추정으로 다시 나눈다
문맥: notes/order-status-request.md
      src/store.ts · src/orders.ts · src/payments.ts · src/admin.ts · src/server.ts
      tests/orders.test.ts · package.json
제약: 코드는 읽기만 한다 · ## 요청 원문은 건드리지 않는다
      정책으로 정한 문장은 코드 사실과 같은 칸에 넣지 않는다
완료 조건: ## 확인된 사실과 ## 추정이 있고, 사실마다 근거 파일 경로가 붙어 있다
```

#### 검증

- [ ] 두 섹션이 모두 존재합니다.
- [ ] 확인된 사실마다 근거 경로가 하나 이상 있습니다.
- [ ] 확인하지 않은 내용은 추정으로 분류했습니다.
- [ ] 대화에서 나온 정책을 코드로 확인된 사실처럼 기록하지 않았습니다.

### E3. 결정 질문 남기기

#### 설계 질문

- 대화에서 결정된 것처럼 보이지만 다시 확인해야 할 정책은 무엇인가요?
- 아직 결정되지 않은 질문마다 가능한 선택지가 두 개 이상 있나요?

#### 실행

대화 속 결정의 근거와 유효 범위를 검토합니다. 다음 작업의 공식 기준으로 확인되지 않은 정책은 `notes/pending-decisions.md`에 질문과 선택지로 기록합니다.

```
목표: 추정 항목을 사람이 답해야 할 결정 질문으로 바꾼다
문맥: notes/order-status-request.md의 ## 추정
제약: 답을 쓰지 않는다 · 선택지만 적는다
완료 조건: notes/pending-decisions.md의 ## 결정이 필요한 질문 아래에
          질문이 3개 이상 있고, 각 질문에 선택지가 2개 이상 있다
```

#### 검증

- [ ] 결정 질문이 세 개 이상 있습니다.
- [ ] 각 질문에 선택지가 두 개 이상 있습니다.
- [ ] 대화에 등장했다는 이유만으로 정책을 공식 기준처럼 확정하지 않았습니다.

### E4. 다음 세션의 시작점 만들기

#### 설계 질문

- 다음 사람이 가장 먼저 읽어야 할 파일은 무엇인가요?
- 다음 작업의 멈춤 지점은 어디인가요?

#### 실행

`notes/next-actions.md`에 다음 작업, 먼저 읽을 파일, 사람 확인이 필요한 지점을 남기고 세 파일을 함께 검토한 뒤 지정된 메시지로 커밋합니다.

```
목표: 다음 세션이 이 파일만 읽고 바로 시작할 수 있게 만든다
문맥: notes/order-status-request.md · notes/pending-decisions.md
제약: 다음 작업은 조사와 정리까지만 — 구현과 정책 결정은 다음 작업이 아니다
      방금 본 세 방향으로 잡는다 — 관련 파일 후보, 현재 동작 정리, 테스트가 안 잡는 것
      src/와 tests/는 바뀌지 않는다 · 커밋은 notes/ 세 파일만
완료 조건: notes/next-actions.md의 ## 다음 작업에 3개 이하가 있고,
          각 작업에 입력 파일이나 확인 대상이 붙어 있다
          사람이 정해야 할 지점은 다음 작업이 아니라 따로 적는다
          node labs/tools/check.mjs 02가 통과한다
```

#### 검증

- [ ] 다음 작업이 세 개 이하의 작은 단위로 적혀 있습니다.
- [ ] 각 작업에 입력 파일 또는 확인 대상이 있습니다.
- [ ] `git status`에 의도하지 않은 코드 변경이 없습니다.
- [ ] 지정된 커밋이 한 개 생성됐습니다.
