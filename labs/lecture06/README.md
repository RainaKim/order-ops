## 3. 실습

### E1. 문서 세트 정리와 handoff 검증

Chapter 1에서 만든 문서는 생성 시점과 역할이 서로 다릅니다. 요청 당시의 추정과 최종 계획이 다른 것은 정상일 수 있지만, 이미 답한 질문이 미결로 남거나 통과한 Human Gate가 승인 전 상태로만 보이면 다음 작업자가 잘못된 지점에서 멈춥니다. 이번 단계에서는 각 정보의 기준 문서를 정하고, 최신 결정 상태를 반영한 뒤 새 Task에서 실제로 이어받을 수 있는지 확인합니다.

#### 이번 단계의 범위

| 구분 | 내용 |
| --- | --- |
| 하는 것 | 문서 역할·충돌을 점검하고, 기존 결정과 Gate 상태를 최신화하고, handoff 진입 문서를 만듭니다. |
| 하지 않는 것 | 새로운 정책 결정, 재사용 template 작성, Codex surface 배정, 구현과 테스트 변경은 하지 않습니다. |
| 종료 상태 | `notes/small-development-workflow.md` 하나로 새 Task가 현재 상태와 바로 다음 작업을 설명할 수 있습니다. |

#### 진행 흐름

```mermaid
flowchart LR
    Audit["문서 역할·충돌 감사"] --> Gate["사람이 실제 충돌 판정"]
    Gate --> Sync["결정·Gate 상태 최신화"]
    Sync --> Entry["workflow 진입 문서 생성"]
    Entry --> Handoff["새 Task에서 handoff 검증"]
    Handoff --> Repair["필요한 연결만 보완"]
```

#### 설계 질문

- 요청·결정·작업 경계·실행 계획·repo 규칙은 각각 어느 문서가 기준인가요?
- 문서 사이의 차이가 정상적인 시간 변화인지 실제 충돌인지 구분할 수 있나요?
- 이미 내린 결정과 통과한 Human Gate가 최신 상태로 표시됐나요?
- 맥락이 없는 새 Task가 진입 문서 하나로 다음 작업을 찾을 수 있나요?

#### 실행

같은 Task에서 `notes/order-status-request.md`, `notes/pending-decisions.md`, `notes/task-boundary.md`, `notes/order-status-plan.md`를 연결합니다. root `AGENTS.md`는 자동으로 적용되는 repo 공통 규칙으로 함께 대조합니다. 먼저 파일을 수정하지 않고 각 문서의 역할, 기준 정보, 읽는 순서, 다른 문서와의 연결, 다음 작업자를 막을 충돌과 누락을 정리합니다.

##### 문서 감사를 읽는 기준

| 관점 | 확인할 질문 |
| --- | --- |
| 역할 | 이 문서는 요청·결정·경계·계획·공통 규칙 중 무엇을 책임지는가? |
| 시간 | 요청 당시의 추정인가, 현재 사실인가, 사람이 승인한 최신 계획인가? |
| 상태 | 질문과 Human Gate가 미결·보류·확정·통과 중 어떤 상태인가? |
| 연결 | 다른 문서의 내용이 필요할 때 복사하지 않고 기준 위치로 연결되는가? |
| 다음 행동 | 다음 작업자가 어느 문서부터 읽고 어디에서 이어가야 하는가? |

초기 요청의 추정과 이후 plan의 차이를 자동으로 충돌 처리하지 않습니다. 반면 `order-status-plan.md`에 이미 반영된 사람 결정이 `pending-decisions.md`에서 계속 미결로 보이거나, 통과한 Gate가 승인 전 상태로만 남아 있다면 실제 handoff 문제로 분류합니다.

##### 사람 확인 — 실제 충돌과 최소 수정

감사 결과를 바로 수정에 사용하지 않고 다음을 확인합니다.

- 요청 원문과 초기 추정은 당시 기록으로 보존할 수 있는가?
- 사람 결정은 한 문서에서 상태와 결과를 추적할 수 있는가?
- 최신 수정·제외 범위와 검증 계획의 기준 문서가 분명한가?
- repo 공통 규칙과 특정 주문 요청의 결정을 섞지 않았는가?
- Human Gate의 질문·승인 전 금지 조건과 현재 통과 상태를 함께 보존할 수 있는가?
- 중복 내용을 늘리지 않고 상태와 링크만 고쳐 해결할 수 있는가?

수정할 충돌을 확인한 뒤에만 기존 결정 기록을 최신화합니다. `pending-decisions.md`는 질문과 선택지를 보존하면서 현재 결정 추적 역할, 처리 상태, 실제 선택 결과, plan 적용 위치를 보여야 합니다. 기존 선택지에 없었지만 E3에서 추가로 확정한 결정은 원래 질문의 선택 결과에 섞지 않고 별도 구역으로 분리합니다.

`task-boundary.md`에는 Human Gate의 통과 상태와 결정·계획 문서 연결만 추가합니다. 사람이 확인했던 질문과 승인 전에 하지 않을 조건은 작업 이력으로 보존하고, 정책 답변을 다시 복사하지 않습니다.

##### 정합 수정 검토

결정 상태와 Gate 기록을 수정한 뒤 다음을 다시 대조합니다.

- 모든 질문의 처리 상태와 실제 선택 결과가 현재 plan에 일치하는가?
- 이번 작업에서 보류한 항목을 답이 없는 미결 상태로 표현하지 않았는가?
- 테스트 범위가 실제 `## 테스트·검증 계획`과 일치하는가?
- 두 Human Gate가 통과 상태이며 결정·계획 문서로 연결되는가?
- 요청 문서의 초기 추정이나 plan의 승인 범위를 덮어쓰지 않았는가?
- `pending-decisions.md`와 `task-boundary.md` 외의 파일을 의도치 않게 수정하지 않았는가?

##### Workflow 진입 문서 만들기

문서 상태가 일치한 뒤 `notes/small-development-workflow.md`를 만듭니다. 이 파일은 요청·결정·계획을 다시 합친 종합 문서가 아니라, 다음 작업자가 기준 문서를 찾아가는 얇은 진입점입니다.

진입 문서에서는 다음 정보를 찾을 수 있어야 합니다.

- 현재 어떤 작업을 이어받는가
- 각 문서의 역할과 기준 정보는 무엇인가
- 어떤 순서로 문서를 읽는가
- Human Gate와 계획은 어디까지 완료됐는가
- 바로 다음 작업은 무엇인가
- 아직 시작하면 안 되는 작업은 무엇인가

E2의 재사용 가능한 8단계 template과 E3의 Codex surface 배정은 아직 작성하지 않습니다. `order-status-plan.md`는 이후 구현의 입력으로 연결하되, Chapter 1에서 구현을 시작한다는 의미로 쓰지 않습니다.

##### 새 Task에서 cold-start handoff 검증

같은 Task는 앞선 대화 맥락을 알고 있으므로 handoff 검증에 사용하지 않습니다. Codex Desktop에서 새 Task를 열고 `notes/small-development-workflow.md` 하나만 연결합니다. 새 Task가 진입 문서의 링크를 따라 필요한 자료를 읽고 다음 내용을 보고할 수 있는지 확인합니다.

- 현재 요청과 확인된 현재 동작
- 사람의 확정·보류 결정
- 수정·제외 범위와 검증 계획
- 현재 멈춘 지점과 바로 다음 작업
- 지금 하면 안 되는 일과 추측하면 안 되는 누락

새 Task가 이미 끝난 결정을 다시 묻거나 바로 구현을 시작하려 한다면, 상세 내용을 진입 문서에 복사하지 않습니다. 결정 상태가 틀리면 결정 문서를, 다음 작업이 모호하면 진입 문서의 해당 연결을 최소한으로 고친 뒤 다시 확인합니다.

##### 왜 이 순서인가

오래된 결정 상태를 그대로 연결하면 진입 문서도 잘못된 handoff를 제공합니다. 먼저 기존 문서의 기준과 현재 상태를 맞추고, 그다음 얇은 진입점을 만든 뒤 맥락이 없는 새 Task에서 시험해야 문서만으로 이어갈 수 있는지 판정할 수 있습니다.

##### 이 단계에서 자주 나오는 실수

- 모든 문서 차이를 충돌로 보고 초기 요청과 추정을 최신 계획으로 덮어씁니다.
- 이미 내린 결정을 새 Human Gate에서 다시 선택합니다.
- Gate 통과 상태를 남기면서 기존 질문과 승인 전 금지 조건을 삭제합니다.
- handoff 문서에 요청·결정·계획의 상세 내용을 다시 복사합니다.
- 같은 Task의 이전 대화 기억으로 handoff 성공을 판단합니다.

#### 검증

- [ ] 결정 추적 문서의 처리 상태와 실제 선택 결과가 현재 plan에 일치합니다.
- [ ] Human Gate 1·2의 질문과 승인 전 조건이 보존되고 통과 상태가 표시됐습니다.
- [ ] `notes/small-development-workflow.md`에서 문서 역할·읽는 순서·다음 작업을 찾을 수 있습니다.
- [ ] 새 Task가 진입 문서 하나로 현재 상태와 다음 작업을 설명했습니다.
- [ ] E2 template과 E3 surface 배정이 미리 작성되지 않았습니다.
- [ ] `src/`, `tests/`에 변경이 없습니다.

### E2. 8단계 workflow skeleton 만들기

E1의 문서 세트는 주문 상태 요청 하나를 이어받기 위한 진입점입니다. 이번 단계에서는 그 내용을 복사하지 않고, 요청이 사실 확인·사람 결정·계획·검증·handoff를 통과한 순서만 추출해 다른 작업에서도 사용할 빈 template으로 만듭니다. 처음부터 파일을 작성하지 않고 섹션의 책임을 먼저 합의한 뒤, 별도 reviewer subagent가 맥락 없이 읽어도 안전한지 확인합니다.

#### 이번 단계의 범위

| 구분 | 내용 |
| --- | --- |
| 하는 것 | 실제 문서 세트에서 8개 섹션의 책임을 추출하고, 빈 workflow template을 작성하고, 독립 리뷰를 반영합니다. |
| 하지 않는 것 | 주문 상태 작업의 답을 복사하거나, 새 정책을 결정하거나, E3의 Codex surface를 배정하지 않습니다. |
| 종료 상태 | `docs/templates/workflow-skeleton.md`가 특정 작업과 무관한 재사용 구조로 완성됩니다. |

#### 진행 흐름

```mermaid
flowchart LR
    Boundary["섹션 책임 경계 설계"] --> Gate1["사람이 경계 승인"]
    Gate1 --> Draft["빈 template 작성"]
    Draft --> Review["reviewer subagent 독립 검토"]
    Review --> Gate2["사람이 반영 항목 선택"]
    Gate2 --> Verify["승인 항목 반영·종료 확인"]
```

#### 설계 질문

- 요청의 표현, 확인된 사실, 실제 동작은 각각 어디에 남겨야 하나요?
- 기존 규칙과 이번 요청에서 새로 생긴 결정은 어떻게 구분해야 하나요?
- 미결 결정이 수정 계획의 전제로 넘어가지 않게 하려면 무엇을 판정해야 하나요?
- 검증 계획과 실제 실행 결과, 현재 멈춘 지점은 어떻게 구분해야 하나요?

#### 실행

E2 시작 시 `git status --short`로 현재 변경 상태를 확인합니다. E1에서 이미 바뀐 `notes/` 파일을 기억해 두고, 이번 단계의 새 변경과 구분합니다.

##### 1. 섹션 책임 경계 설계

`notes/small-development-workflow.md`와 `labs/CONVENTIONS.md`를 연결합니다. 진입 문서가 가리키는 기준 문서를 따라가며 다음 8개 섹션의 목적, 입력 근거, 작성 질문, 남겨야 할 결과, 이웃 섹션과의 구분을 먼저 표로 정리합니다. 아직 파일은 작성하지 않습니다.

1. 요청 원문
2. 현재 파악
3. 관련 맥락
4. 현재 동작
5. 결정 필요 사항
6. 수정 계획
7. 검증 기준
8. 다음 단계

주문 상태 작업은 구조를 찾기 위한 사례로만 사용합니다. 상태 이름, API 응답, 재고 정책처럼 이미 확정된 답을 template 내용으로 옮기지 않습니다.

##### 사람 확인 — 책임 경계

작성된 표에서 다음을 확인합니다.

- `요청 원문`은 해석 전 출처를 보존하고 `현재 파악`은 이해와 남은 공백을 구분하는가?
- 흐름별 코드 동작은 `현재 파악`이 아니라 `현재 동작`에 있는가?
- `관련 맥락`은 기존 기준을 연결하고 `결정 필요 사항`은 이번 요청의 결정 상태를 추적하는가?
- `검증 기준`은 계획·실행·미실행을 구분하고 `다음 단계`는 현재 멈춘 지점을 남기는가?

##### 2. 빈 workflow template 작성

승인한 경계를 사용해 `docs/templates/workflow-skeleton.md`를 작성합니다. `docs/`는 여러 작업에서 다시 읽는 오래 사는 기준이므로 이번 lab에서 처음 생성합니다.

각 섹션에는 다음 세 요소가 있어야 합니다.

- 이 섹션이 필요한 이유를 설명하는 목적
- 작성할 때 답해야 하는 질문
- 다음 단계로 넘어갈 수 있는 완료 판정

완성된 주문 상태 답안이나 입력 예시는 넣지 않습니다. 렌더링된 Markdown에서 8개 섹션이 같은 계층과 반복 구조로 읽히는지 확인하고, 명백한 구조 오류가 없다면 문장을 계속 다듬지 않고 독립 리뷰로 넘깁니다.

##### 3. reviewer subagent 독립 검토

reviewer subagent 하나에 작성된 template만 검토하게 합니다. reviewer는 파일을 수정하지 않고 다음 작업자가 잘못 움직일 가능성만 보고합니다.

- 확인된 사실과 해석·가설이 섞이는가?
- 사람 결정 전에 수정 계획이 확정될 수 있는가?
- 섹션 사이에 중복이나 책임 공백이 있는가?
- 계획한 검증을 실행 결과로 오인할 수 있는가?
- 현재 멈춘 지점과 다음 행동을 찾을 수 있는가?
- 특정 주문 상태 작업에 종속된 표현이 있는가?

각 문제에는 관련 섹션, 다음 작업자에게 미치는 영향, 최소 수정 제안이 있어야 합니다. 문제가 없는 항목을 채우기 위해 새 문제를 만들지 않습니다.

##### 사람 확인 — 리뷰 반영

리뷰 결과를 자동으로 모두 반영하지 않습니다. 다음 작업자의 결정·검증·handoff를 실제로 바꿀 문제인지 확인하고, 기존 섹션의 질문이나 완료 판정으로 해결할 수 있는 항목만 승인합니다. 승인한 항목은 이 단계 안에서 즉시 반영하며 별도의 수정 단계를 다시 만들지 않습니다.

`현재 파악`에서 요청 해석이 확인된 사실처럼 사용될 수 있다면, 해석과 확인 전 가설을 구분하고 확인된 사실은 근거 또는 `현재 동작`의 해당 항목으로 연결하게 합니다. 실제 동작을 두 섹션에 복사하지 않습니다.

##### 종료 확인

마지막 확인은 파일을 수정하지 않는 읽기 전용 작업입니다. 정확한 8개 섹션, 섹션별 목적·작성 질문·완료 판정, 특정 사례 비포함, E2 변경 범위, `src/`·`tests/` 무변경을 항목별로 판정합니다. E1에서 이미 존재하던 변경을 E2 변경으로 오인하지 않습니다.

`node labs/tools/check.mjs 06`은 E3와 E4까지 완료한 뒤 실행합니다.

##### 왜 이 순서인가

섹션 경계를 먼저 승인하면 중복된 구조를 파일 전체에 퍼뜨리지 않습니다. 작성자와 다른 subagent가 template만 읽으면 이전 대화가 가려 주던 공백을 찾을 수 있고, 사람이 반영 범위를 선택하면 리뷰 때문에 template이 불필요하게 커지는 것도 막을 수 있습니다.

##### 이 단계에서 자주 나오는 실수

- E1의 주문 상태 내용을 template의 작성 예시로 복사합니다.
- `현재 파악`과 `현재 동작`에 같은 코드 사실을 반복합니다.
- reviewer의 모든 제안을 사람 확인 없이 반영합니다.
- 리뷰 반영 뒤 같은 내용을 별도의 수정 단계에서 다시 고칩니다.

- [ ] 모든 섹션에 목적·작성 질문·완료 판정이 있습니다.
- [ ] 특정 주문 상태 작업의 정책과 완성 답안이 들어 있지 않습니다.
