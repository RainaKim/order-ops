## 3. 실습

### E1. 문서 세트 정리와 handoff 검증

Chapter 1에서 만든 문서는 생성 시점과 역할이 서로 다릅니다. 요청 당시의 추정과 최종 계획이 다른 것은 정상일 수 있지만, 이미 답한 질문이 미결로 남거나 통과한 Human Gate가 승인 전 상태로만 보이면 다음 작업자가 잘못된 지점에서 멈춥니다. 이번 단계에서는 각 정보의 기준 문서를 정하고, 최신 결정 상태를 반영한 뒤 새 Task에서 실제로 이어받을 수 있는지 확인합니다.

#### 이번 단계의 범위

| 구분 | 내용 |
| --- | --- |
| 하는 것 | 문서 역할·충돌을 점검하고, 기존 결정과 Gate 상태를 최신화하고, handoff 진입 문서를 만듭니다. |
| 하지 않는 것 | 새로운 정책 결정, 재사용 template 작성, Codex surface 배정, 구현과 테스트 변경은 하지 않습니다. |
| 종료 상태 | `notes/small-development-workflow.md` 하나로 새 Task가 현재 상태와 바로 다음 작업을 설명할 수 있습니다. |

#### 진행 흐름

```mermaid
flowchart LR
    Audit["문서 역할·충돌 감사"] --> Gate["사람이 실제 충돌 판정"]
    Gate --> Sync["결정·Gate 상태 최신화"]
    Sync --> Entry["workflow 진입 문서 생성"]
    Entry --> Handoff["새 Task에서 handoff 검증"]
    Handoff --> Repair["필요한 연결만 보완"]
```

#### 설계 질문

- 요청·결정·작업 경계·실행 계획·repo 규칙은 각각 어느 문서가 기준인가요?
- 문서 사이의 차이가 정상적인 시간 변화인지 실제 충돌인지 구분할 수 있나요?
- 이미 내린 결정과 통과한 Human Gate가 최신 상태로 표시됐나요?
- 맥락이 없는 새 Task가 진입 문서 하나로 다음 작업을 찾을 수 있나요?

#### 실행

같은 Task에서 `notes/order-status-request.md`, `notes/pending-decisions.md`, `notes/task-boundary.md`, `notes/order-status-plan.md`를 연결합니다. root `AGENTS.md`는 자동으로 적용되는 repo 공통 규칙으로 함께 대조합니다. 먼저 파일을 수정하지 않고 각 문서의 역할, 기준 정보, 읽는 순서, 다른 문서와의 연결, 다음 작업자를 막을 충돌과 누락을 정리합니다.

##### 문서 감사를 읽는 기준

| 관점 | 확인할 질문 |
| --- | --- |
| 역할 | 이 문서는 요청·결정·경계·계획·공통 규칙 중 무엇을 책임지는가? |
| 시간 | 요청 당시의 추정인가, 현재 사실인가, 사람이 승인한 최신 계획인가? |
| 상태 | 질문과 Human Gate가 미결·보류·확정·통과 중 어떤 상태인가? |
| 연결 | 다른 문서의 내용이 필요할 때 복사하지 않고 기준 위치로 연결되는가? |
| 다음 행동 | 다음 작업자가 어느 문서부터 읽고 어디에서 이어가야 하는가? |

초기 요청의 추정과 이후 plan의 차이를 자동으로 충돌 처리하지 않습니다. 반면 `order-status-plan.md`에 이미 반영된 사람 결정이 `pending-decisions.md`에서 계속 미결로 보이거나, 통과한 Gate가 승인 전 상태로만 남아 있다면 실제 handoff 문제로 분류합니다.

##### 사람 확인 — 실제 충돌과 최소 수정

감사 결과를 바로 수정에 사용하지 않고 다음을 확인합니다.

- 요청 원문과 초기 추정은 당시 기록으로 보존할 수 있는가?
- 사람 결정은 한 문서에서 상태와 결과를 추적할 수 있는가?
- 최신 수정·제외 범위와 검증 계획의 기준 문서가 분명한가?
- repo 공통 규칙과 특정 주문 요청의 결정을 섞지 않았는가?
- Human Gate의 질문·승인 전 금지 조건과 현재 통과 상태를 함께 보존할 수 있는가?
- 중복 내용을 늘리지 않고 상태와 링크만 고쳐 해결할 수 있는가?

수정할 충돌을 확인한 뒤에만 기존 결정 기록을 최신화합니다. `pending-decisions.md`는 질문과 선택지를 보존하면서 현재 결정 추적 역할, 처리 상태, 실제 선택 결과, plan 적용 위치를 보여야 합니다. 기존 선택지에 없었지만 E3에서 추가로 확정한 결정은 원래 질문의 선택 결과에 섞지 않고 별도 구역으로 분리합니다.

`task-boundary.md`에는 Human Gate의 통과 상태와 결정·계획 문서 연결만 추가합니다. 사람이 확인했던 질문과 승인 전에 하지 않을 조건은 작업 이력으로 보존하고, 정책 답변을 다시 복사하지 않습니다.

##### 정합 수정 검토

결정 상태와 Gate 기록을 수정한 뒤 다음을 다시 대조합니다.

- 모든 질문의 처리 상태와 실제 선택 결과가 현재 plan에 일치하는가?
- 이번 작업에서 보류한 항목을 답이 없는 미결 상태로 표현하지 않았는가?
- 테스트 범위가 실제 `## 테스트·검증 계획`과 일치하는가?
- 두 Human Gate가 통과 상태이며 결정·계획 문서로 연결되는가?
- 요청 문서의 초기 추정이나 plan의 승인 범위를 덮어쓰지 않았는가?
- `pending-decisions.md`와 `task-boundary.md` 외의 파일을 의도치 않게 수정하지 않았는가?

##### Workflow 진입 문서 만들기

문서 상태가 일치한 뒤 `notes/small-development-workflow.md`를 만듭니다. 이 파일은 요청·결정·계획을 다시 합친 종합 문서가 아니라, 다음 작업자가 기준 문서를 찾아가는 얇은 진입점입니다.

진입 문서에서는 다음 정보를 찾을 수 있어야 합니다.

- 현재 어떤 작업을 이어받는가
- 각 문서의 역할과 기준 정보는 무엇인가
- 어떤 순서로 문서를 읽는가
- Human Gate와 계획은 어디까지 완료됐는가
- 바로 다음 작업은 무엇인가
- 아직 시작하면 안 되는 작업은 무엇인가

E2의 재사용 가능한 8단계 template과 E3의 Codex surface 배정은 아직 작성하지 않습니다. `order-status-plan.md`는 이후 구현의 입력으로 연결하되, Chapter 1에서 구현을 시작한다는 의미로 쓰지 않습니다.

##### 새 Task에서 cold-start handoff 검증

같은 Task는 앞선 대화 맥락을 알고 있으므로 handoff 검증에 사용하지 않습니다. Codex Desktop에서 새 Task를 열고 `notes/small-development-workflow.md` 하나만 연결합니다. 새 Task가 진입 문서의 링크를 따라 필요한 자료를 읽고 다음 내용을 보고할 수 있는지 확인합니다.

- 현재 요청과 확인된 현재 동작
- 사람의 확정·보류 결정
- 수정·제외 범위와 검증 계획
- 현재 멈춘 지점과 바로 다음 작업
- 지금 하면 안 되는 일과 추측하면 안 되는 누락

새 Task가 이미 끝난 결정을 다시 묻거나 바로 구현을 시작하려 한다면, 상세 내용을 진입 문서에 복사하지 않습니다. 결정 상태가 틀리면 결정 문서를, 다음 작업이 모호하면 진입 문서의 해당 연결을 최소한으로 고친 뒤 다시 확인합니다.

##### 왜 이 순서인가

오래된 결정 상태를 그대로 연결하면 진입 문서도 잘못된 handoff를 제공합니다. 먼저 기존 문서의 기준과 현재 상태를 맞추고, 그다음 얇은 진입점을 만든 뒤 맥락이 없는 새 Task에서 시험해야 문서만으로 이어갈 수 있는지 판정할 수 있습니다.

##### 이 단계에서 자주 나오는 실수

- 모든 문서 차이를 충돌로 보고 초기 요청과 추정을 최신 계획으로 덮어씁니다.
- 이미 내린 결정을 새 Human Gate에서 다시 선택합니다.
- Gate 통과 상태를 남기면서 기존 질문과 승인 전 금지 조건을 삭제합니다.
- handoff 문서에 요청·결정·계획의 상세 내용을 다시 복사합니다.
- 같은 Task의 이전 대화 기억으로 handoff 성공을 판단합니다.

#### 검증

- [ ] 결정 추적 문서의 처리 상태와 실제 선택 결과가 현재 plan에 일치합니다.
- [ ] Human Gate 1·2의 질문과 승인 전 조건이 보존되고 통과 상태가 표시됐습니다.
- [ ] `notes/small-development-workflow.md`에서 문서 역할·읽는 순서·다음 작업을 찾을 수 있습니다.
- [ ] 새 Task가 진입 문서 하나로 현재 상태와 다음 작업을 설명했습니다.
- [ ] E2 template과 E3 surface 배정이 미리 작성되지 않았습니다.
- [ ] `src/`, `tests/`에 변경이 없습니다.

### E2. 8단계 workflow skeleton 만들기

E1의 문서 세트는 주문 상태 요청 하나를 이어받기 위한 진입점입니다. 이번 단계에서는 그 내용을 복사하지 않고, 요청이 사실 확인·사람 결정·계획·검증·handoff를 통과한 순서만 추출해 다른 작업에서도 사용할 빈 template으로 만듭니다. 처음부터 파일을 작성하지 않고 섹션의 책임을 먼저 합의한 뒤, 별도 reviewer subagent가 맥락 없이 읽어도 안전한지 확인합니다.

#### 이번 단계의 범위

| 구분 | 내용 |
| --- | --- |
| 하는 것 | 실제 문서 세트에서 8개 섹션의 책임을 추출하고, 빈 workflow template을 작성하고, 독립 리뷰를 반영합니다. |
| 하지 않는 것 | 주문 상태 작업의 답을 복사하거나, 새 정책을 결정하거나, E3의 Codex surface를 배정하지 않습니다. |
| 종료 상태 | `docs/templates/workflow-skeleton.md`가 특정 작업과 무관한 재사용 구조로 완성됩니다. |

#### 진행 흐름

```mermaid
flowchart LR
    Boundary["섹션 책임 경계 설계"] --> Gate1["사람이 경계 승인"]
    Gate1 --> Draft["빈 template 작성"]
    Draft --> Review["reviewer subagent 독립 검토"]
    Review --> Gate2["사람이 반영 항목 선택"]
    Gate2 --> Verify["승인 항목 반영·종료 확인"]
```

#### 설계 질문

- 요청의 표현, 확인된 사실, 실제 동작은 각각 어디에 남겨야 하나요?
- 기존 규칙과 이번 요청에서 새로 생긴 결정은 어떻게 구분해야 하나요?
- 미결 결정이 수정 계획의 전제로 넘어가지 않게 하려면 무엇을 판정해야 하나요?
- 검증 계획과 실제 실행 결과, 현재 멈춘 지점은 어떻게 구분해야 하나요?

#### 실행

E2 시작 시 `git status --short`로 현재 변경 상태를 확인합니다. E1에서 이미 바뀐 `notes/` 파일을 기억해 두고, 이번 단계의 새 변경과 구분합니다.

##### 1. 섹션 책임 경계 설계

`notes/small-development-workflow.md`와 `labs/CONVENTIONS.md`를 연결합니다. 진입 문서가 가리키는 기준 문서를 따라가며 다음 8개 섹션의 목적, 입력 근거, 작성 질문, 남겨야 할 결과, 이웃 섹션과의 구분을 먼저 표로 정리합니다. 아직 파일은 작성하지 않습니다.

1. 요청 원문
2. 현재 파악
3. 관련 맥락
4. 현재 동작
5. 결정 필요 사항
6. 수정 계획
7. 검증 기준
8. 다음 단계

주문 상태 작업은 구조를 찾기 위한 사례로만 사용합니다. 상태 이름, API 응답, 재고 정책처럼 이미 확정된 답을 template 내용으로 옮기지 않습니다.

##### 사람 확인 — 책임 경계

작성된 표에서 다음을 확인합니다.

- `요청 원문`은 해석 전 출처를 보존하고 `현재 파악`은 이해와 남은 공백을 구분하는가?
- 흐름별 코드 동작은 `현재 파악`이 아니라 `현재 동작`에 있는가?
- `관련 맥락`은 기존 기준을 연결하고 `결정 필요 사항`은 이번 요청의 결정 상태를 추적하는가?
- `검증 기준`은 계획·실행·미실행을 구분하고 `다음 단계`는 현재 멈춘 지점을 남기는가?

##### 2. 빈 workflow template 작성

승인한 경계를 사용해 `docs/templates/workflow-skeleton.md`를 작성합니다. `docs/`는 여러 작업에서 다시 읽는 오래 사는 기준이므로 이번 lab에서 처음 생성합니다.

각 섹션에는 다음 세 요소가 있어야 합니다.

- 이 섹션이 필요한 이유를 설명하는 목적
- 작성할 때 답해야 하는 질문
- 다음 단계로 넘어갈 수 있는 완료 판정

완성된 주문 상태 답안이나 입력 예시는 넣지 않습니다. 렌더링된 Markdown에서 8개 섹션이 같은 계층과 반복 구조로 읽히는지 확인하고, 명백한 구조 오류가 없다면 문장을 계속 다듬지 않고 독립 리뷰로 넘깁니다.

##### 3. reviewer subagent 독립 검토

reviewer subagent 하나에 작성된 template만 검토하게 합니다. reviewer는 파일을 수정하지 않고 다음 작업자가 잘못 움직일 가능성만 보고합니다.

- 확인된 사실과 해석·가설이 섞이는가?
- 사람 결정 전에 수정 계획이 확정될 수 있는가?
- 섹션 사이에 중복이나 책임 공백이 있는가?
- 계획한 검증을 실행 결과로 오인할 수 있는가?
- 현재 멈춘 지점과 다음 행동을 찾을 수 있는가?
- 특정 주문 상태 작업에 종속된 표현이 있는가?

각 문제에는 관련 섹션, 다음 작업자에게 미치는 영향, 최소 수정 제안이 있어야 합니다. 문제가 없는 항목을 채우기 위해 새 문제를 만들지 않습니다.

##### 사람 확인 — 리뷰 반영

리뷰 결과를 자동으로 모두 반영하지 않습니다. 다음 작업자의 결정·검증·handoff를 실제로 바꿀 문제인지 확인하고, 기존 섹션의 질문이나 완료 판정으로 해결할 수 있는 항목만 승인합니다. 승인한 항목은 이 단계 안에서 즉시 반영하며 별도의 수정 단계를 다시 만들지 않습니다.

`현재 파악`에서 요청 해석이 확인된 사실처럼 사용될 수 있다면, 해석과 확인 전 가설을 구분하고 확인된 사실은 근거 또는 `현재 동작`의 해당 항목으로 연결하게 합니다. 실제 동작을 두 섹션에 복사하지 않습니다.

##### 종료 확인

마지막 확인은 파일을 수정하지 않는 읽기 전용 작업입니다. 정확한 8개 섹션, 섹션별 목적·작성 질문·완료 판정, 특정 사례 비포함, E2 변경 범위, `src/`·`tests/` 무변경을 항목별로 판정합니다. E1에서 이미 존재하던 변경을 E2 변경으로 오인하지 않습니다.

`node labs/tools/check.mjs 06`은 E3와 E4까지 완료한 뒤 실행합니다.

##### 왜 이 순서인가

섹션 경계를 먼저 승인하면 중복된 구조를 파일 전체에 퍼뜨리지 않습니다. 작성자와 다른 subagent가 template만 읽으면 이전 대화가 가려 주던 공백을 찾을 수 있고, 사람이 반영 범위를 선택하면 리뷰 때문에 template이 불필요하게 커지는 것도 막을 수 있습니다.

##### 이 단계에서 자주 나오는 실수

- `현재 파악`과 `현재 동작`에 같은 코드 사실을 반복합니다.
- reviewer의 모든 제안을 사람 확인 없이 반영합니다.
- 리뷰 반영 뒤 같은 내용을 별도의 수정 단계에서 다시 고칩니다.

### E3. Codex surface 연결하기

Workflow의 모든 단계를 같은 화면에서 처리할 필요는 없습니다. 긴 문맥과 사람 결정은 Desktop App에서 이어가고, 로컬 저장소의 실행 가능성은 Codex CLI에서 확인할 수 있습니다. Browser와 Computer Use는 실제 화면이 필요한 경우에만 선택하며, 반복성이 확인되지 않은 작업은 Scheduled task로 만들지 않습니다. 이번 단계에서는 surface를 많이 사용하는 대신, 작업 성격이 바뀌는 경계에서 정확히 handoff하는 방법을 연습합니다.

#### 이번 단계의 범위

| 구분 | 내용 |
| --- | --- |
| 하는 것 | 공식 기능을 확인하고, workflow 작업에 surface를 배정하고, Desktop에서 CLI로 handoff한 뒤 `/review`로 변경을 검토합니다. |
| 하지 않는 것 | 구현·테스트 변경, 검증 명령 실행, 실제 Scheduled task 생성은 하지 않습니다. |
| 종료 상태 | `notes/small-development-workflow.md`에서 각 작업의 입력·증거·사람 확인·다음 handoff와 구현 차단 조건을 찾을 수 있습니다. |

#### 진행 흐름

```mermaid
flowchart LR
    Research["공식 기능 확인"] --> Allocate["작업별 surface 배정"]
    Allocate --> Gate["사람이 배정 승인"]
    Gate --> Write["workflow 문서 반영"]
    Write --> CLI["새 CLI 세션에서 handoff 시험"]
    CLI --> Review["/review · 승인 · 수정 · 재검토"]
```

#### 설계 질문

- 긴 문맥과 사람 판단이 필요한 작업은 어디에서 이어가야 하나요?
- 명령 결과와 종료 코드로 판정할 작업은 어느 surface가 적합한가요?
- Browser와 Computer Use가 필요한 실제 화면 또는 GUI 동작이 있나요?
- 한 번의 작업을 Scheduled task 후보로 올릴 만큼 반복성과 중단 조건이 확인됐나요?

#### 실행

E3 시작 시 현재 변경 상태를 확인합니다. E1·E2 산출물은 기준선으로 두고, 이번 단계에서는 `notes/small-development-workflow.md`만 수정합니다.

##### 1. 공식 기능에서 선택 기준 찾기

`$openai-docs`를 사용해 Desktop App, Codex CLI, Browser, Computer Use, Scheduled tasks의 현재 역할과 제약을 확인합니다. 아직 workflow 단계에 surface를 배정하거나 repo 파일을 수정하지 않습니다.

조사 결과에는 surface별로 다음 항목이 있어야 합니다.

- 적합한 작업과 부적합한 작업
- 시작할 때 필요한 입력
- 사람이 정하거나 승인할 행동
- 판단을 뒷받침하는 공식 근거

Browser는 웹사이트나 로컬 웹 앱을 확인하는 작업 공간이고, Computer Use는 명령이나 구조화된 연동으로 충분하지 않을 때 GUI를 조작하는 기능입니다. Scheduled tasks는 Desktop 또는 Web에서 관리하며, 로컬 프로젝트를 사용하는 경우 컴퓨터와 앱의 실행 상태도 조건이 됩니다. 예약 전에 일반 Task나 CLI에서 프롬프트와 절차를 먼저 검증해야 합니다.

##### 2. Workflow를 작업 단위로 묶어 배정하기

`docs/templates/workflow-skeleton.md`, `notes/small-development-workflow.md`, `notes/order-status-plan.md`를 함께 읽습니다. 8개 섹션을 한 행씩 옮기지 않고, 같은 문맥과 surface를 사용하는 연속 단계를 실제 작업 단위로 묶습니다.

배정표에는 다음 항목을 남깁니다.

| 항목 | 판정할 내용 |
| --- | --- |
| 작업 묶음 | 같은 입력과 맥락을 공유하는 단계인가? |
| Primary surface | 이 작업의 주 작업 공간은 어디인가? |
| 입력 | 어떤 문서·파일·명령·화면에서 시작하는가? |
| 산출물 또는 증거 | 다음 작업이 무엇을 근거로 이어가는가? |
| 사람 확인 | 정책·범위·외부 변경처럼 실제 사람 판단이 필요한가? |
| 다음 handoff | 다음 surface가 추측하지 않도록 무엇을 넘기는가? |

현재 저장소는 API 중심이므로 주문 동작의 정확성을 Browser나 Computer Use에 배정하지 않습니다. 이후 원격 변경이 생겼을 때 GitHub의 렌더링된 Markdown, diff, checks 상태는 Browser 확인 후보가 될 수 있습니다. 구조화된 Browser 접근으로 충분하다면 Computer Use는 사용하지 않습니다.

Scheduled task는 구현 후 수동 검증이 통과하고 반복 필요가 생겼을 때만 후보로 둡니다. 실행 주기, project 또는 worktree, 권한, 보고 범위는 생성 전에 사람이 승인해야 하며, 검증 실패나 명령·정책·범위 변경이 발생하면 후속 실행을 중단하고 재승인을 받도록 설계합니다. 이번에는 실제 예약을 만들지 않습니다.

##### 사람 확인 — Surface 배정

배정안을 문서에 쓰기 전에 다음을 확인합니다.

- 긴 문맥과 정책 판단이 Desktop에 남아 있는가?
- 구현과 명령 검증이 E3의 현재 실행이 아니라 향후 CLI handoff로 표시됐는가?
- Codex 자체 점검을 불필요한 Human Gate로 만들지 않았는가?
- Browser 후보에는 실제 확인할 화면이 있는가?
- Scheduled task 후보에는 수동 검증, 반복 조건, 중단 조건, 사람 승인이 있는가?
- 각 surface의 출력이 다음 surface의 입력으로 충분한가?

문제가 있다면 잘못 배정된 작업 묶음만 고칩니다. Surface를 모두 한 번씩 사용하기 위해 정상적인 배정까지 다시 만들지 않습니다.

##### 3. Workflow 진입 문서에 연결하기

승인한 배정안을 `notes/small-development-workflow.md`에 반영합니다. 요청·결정·계획의 상세 내용을 다시 복사하지 않고 기존 기준 문서로 연결합니다.

`## 현재 멈춘 지점`과 `## 바로 다음 작업`에서는 두 흐름을 구분합니다.

- Lab 진행에서는 E3 surface 연결을 완료하고 E4로 넘어갑니다.
- 향후 제품 구현은 CLI handoff의 입력과 차단 조건을 모두 충족해야 시작할 수 있습니다.

재고 부족·재결제 거부 응답과 실패 정보의 세부 계약처럼 구현에 필요한 미결 사항은 Codex가 임의로 정하지 않습니다. 필요한 계약이 없으면 CLI가 구현을 시작하지 않고 사람에게 필요한 결정을 보고하도록 연결합니다.

##### 4. 새 Codex CLI 세션에서 Handoff 시험하기

저장소 root에서 새 Codex CLI 프로세스를 시작합니다. `AGENTS.md`와 `package.json`이 있는 위치인지 확인하고 `notes/small-development-workflow.md` 하나를 진입점으로 제공합니다. 같은 Desktop Task에 CLI의 입장을 흉내 내게 하는 것은 독립 handoff 시험이 아닙니다.

CLI는 파일을 수정하거나 검증 명령을 실행하지 않고 다음 항목의 충족 여부만 판정합니다.

- 저장소 root와 상대 경로 해석
- 구현 입력과 승인된 수정·제외 범위
- 실행할 명령과 순서
- 명령별 통과 기준
- 코드·테스트 실패와 미결 정책 실패를 구분한 정지 조건
- 멈춘 뒤 남길 결과와 구현 재개 조건

누락이 발견되면 답을 추측하지 않습니다. 사람이 finding을 승인한 뒤, 누락된 handoff 항목만 보완합니다. 이때 E3 문서화 완료와 실제 구현 시작 가능 상태를 구분합니다. 구현이 차단되어 있어도 차단 이유와 재개 조건이 정확히 연결됐다면 E3의 handoff 설계는 완료할 수 있습니다.

##### 5. 같은 CLI에서 `/review` 루프 닫기

`/review`는 스킬이 아니라 Desktop App과 Codex CLI에서 제공되는 전용 review 명령입니다. 이번 단계에서는 CLI의 `Custom review instructions`를 사용해 `notes/small-development-workflow.md`의 E3 변경만 검토합니다. 현재 작업 트리의 다른 uncommitted·untracked 파일을 E3 finding으로 섞지 않도록 파일과 검토 기준을 제한합니다.

Reviewer는 우선순위가 있는 finding을 보고하지만 파일을 수정하지 않습니다. 사람이 반영할 finding을 고른 뒤에는 Desktop으로 다시 이동할 필요 없이 같은 CLI 세션의 주 agent에게 승인된 finding만 수정하게 합니다. 수정 후 `/review`를 다시 실행해 기존 finding이 해결됐는지 확인합니다.

Review에서는 다음을 중점적으로 확인합니다.

- CLI handoff에 저장소 root·입력·통과 기준·정지 조건·구현 차단 조건이 있는가?
- Browser가 API 정확성 검증을 대신하지 않는가?
- Computer Use가 GUI 조작이 필요한 경우에만 배정됐는가?
- Scheduled task 후보에 사람 승인·중단·재개 조건이 있는가?
- 실제 구현·명령 실행·예약 생성이 추가되지 않았는가?

Surface는 review와 수정이 반복될 때마다 바꾸지 않습니다. 작업의 성격이 달라지는 경계에서 handoff하고, review·승인·수정·재검토는 필요한 맥락을 가진 같은 surface에서 마무리합니다.

##### 왜 이 순서인가

공식 제약을 먼저 확인해야 기능 이름만 보고 잘못 배정하는 일을 줄일 수 있습니다. Desktop에서 승인된 작업 경계를 만든 뒤 새로운 CLI 세션으로 넘기면 문서만으로 실행 가능성을 판정할 수 있고, `/review` 루프를 같은 CLI에서 닫으면 불필요한 surface 왕복 없이 독립 검토를 유지할 수 있습니다.

##### 이 단계에서 자주 나오는 실수

- 8개 workflow 섹션을 작업 묶음 없이 surface 표에 그대로 옮깁니다.
- 모든 surface를 사용하기 위해 API 검증을 Browser나 Computer Use에 배정합니다.
- 수동 검증 전 Scheduled task를 만들거나 실패한 예약의 중단 조건을 생략합니다.
- review finding이 나올 때마다 Desktop과 CLI를 왕복합니다.

#### 검증

- [ ] 작업 묶음마다 primary surface·입력·증거·사람 확인·다음 handoff가 있습니다.
- [ ] CLI handoff에 저장소 root·통과 기준·정지 조건·구현 차단 조건이 있습니다.
- [ ] Browser와 Computer Use는 실제 화면 또는 GUI 조작이 필요한 경우에만 배정됐습니다.
- [ ] Scheduled task 후보에 수동 검증·반복 조건·사람 승인·중단·재개 조건이 있습니다.
- [ ] `/review`에서 사람이 승인한 finding만 같은 CLI 세션에서 반영됐습니다.
- [ ] 실제 구현·검증 명령·Scheduled task 생성과 `src/`, `tests/` 변경이 없습니다.


처음에는 “결제 실패 상태를 개선해 달라”는 요청만 있었습니다. Chapter 1의 끝에서는 요청 원문, 확인된 현재 동작, 사람이 확정한 정책, 수정·제외 범위, 검증 기준, 다음 작업의 입력과 정지 조건이 서로 다른 역할의 문서로 연결돼 있습니다.

#### 네 가지 실패 패턴에 대응한 장치

| Lab 01에서 확인한 실패 | Chapter 1에서 만든 장치 | 다음 작업에서 달라지는 점 |
| --- | --- | --- |
| 이전 설명과 결정이 새 Task에서 사라집니다. | 요청 기록, 결정 추적, 작업 경계와 `small-development-workflow.md`가 읽는 순서와 현재 멈춘 지점을 연결합니다. | 대화를 기억할 것이라고 기대하지 않고 문서에서 출발합니다. |
| Codex가 미결 정책을 임의로 정합니다. | `pending-decisions.md`, Human Gate와 `AGENTS.md`의 Rules가 사람 결정 전 진행을 막습니다. | 사실 확인과 정책 선택을 분리하고, 승인되지 않은 선택이 필요하면 멈춥니다. |
| 완료 여부를 판단할 검수 근거가 없습니다. | 현재 동작 표, 수정 범위의 완료 경계, 테스트 시나리오와 명령별 통과·정지 기준을 계획에 남깁니다. | “고쳤다”는 설명 대신 관찰 결과와 명령 결과로 완료를 판정합니다. |
| 대화가 다음 작업에서 쓸 자산으로 남지 않습니다. | 요청별 기록은 `notes/`, 재사용 가능한 구조는 `docs/templates/`, repo 공통 규칙은 `AGENTS.md`에 둡니다. | 한 요청에서 만든 판단 구조를 다음 작업에도 재사용할 수 있습니다. |

#### 문서 세트의 역할

| 기준 문서 | 맡은 역할 |
| --- | --- |
| `notes/order-status-request.md` | 요청 원문과 최초 완료 조건을 보존합니다. |
| `notes/pending-decisions.md` | 사람에게 물었던 질문과 확정·보류 상태를 추적합니다. |
| `notes/task-boundary.md` | Human Gate, 작업 단계와 스스로 멈출 조건을 남깁니다. |
| `AGENTS.md` | 어느 Task에서나 적용할 읽기·금지·검증·보고 규칙을 제공합니다. |
| `notes/order-status-plan.md` | 이번 요청의 현재 동작, 수정·제외 범위와 검증 계획을 연결합니다. |
| `notes/small-development-workflow.md` | 현재 작업의 진입점과 다음 handoff를 안내합니다. |
| `docs/templates/workflow-skeleton.md` | 같은 과정을 다른 작은 개발 요청에서도 다시 쓰게 합니다. |

#### Chapter 1의 종료 상태

지금까지 완성한 것은 구현 코드가 아니라 **흔들리지 않는 구현 입력**입니다. 다음 작업자는 무엇을 읽고, 어떤 결정을 따르고, 어디까지 바꾸며, 무엇으로 완료를 판정하고, 어느 조건에서 멈춰야 하는지 확인할 수 있습니다.

반면 `src/`와 `tests/`의 실제 변경, 구현 후 `npm test`·`npm run typecheck`·`npm run lint` 실행, Scheduled task 생성은 아직 하지 않았습니다. Lab 06 E3 완료와 제품 구현 승인은 서로 다른 상태이며, 구현은 별도의 사람 승인과 handoff 조건을 충족한 뒤 시작합니다.

#### 검증

E4에서 새로 검증할 파일이나 명령은 없습니다. 다음 세 문장이 Chapter 1의 종료 상태와 일치하는지만 확인합니다.

- [ ] 네 가지 실패 패턴마다 이를 줄이는 문서 또는 작업 경계가 있습니다.
- [ ] 요청별 기록, 재사용 template과 repo 공통 규칙의 역할이 구분됩니다.
- [ ] 구현 입력은 준비됐지만 실제 코드 변경과 구현 후 검증은 아직 시작하지 않았습니다.
