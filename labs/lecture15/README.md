# Lab 15 — No Silent Fallback

## 0. 이 랩이 끝나면

- 실패를 성공 모양으로 바꾸는 두 silent fallback을 찾아 제거합니다.
- 재시도할 실패와 즉시 멈출 실패를 구분합니다.
- `docs/checklists/failure-handling.md`, `docs/retry-stop-matrix.md`를 만듭니다.
- 예상 소요 시간은 40분입니다.

## 1. 시작 전 상태 확인

- 14강 테스트 세 파일과 assertion review가 있어야 합니다.
- `src/payments.ts`에는 예외를 `ok:false`로 바꾸는 catch가 남아 있습니다.
- `src/admin.ts`에는 예외를 빈 배열로 바꾸는 fallback이 남아 있습니다.

## 3. 실습

### E1. Silent fallback 찾기

#### 설계 질문

- 실제 실패인데 정상 응답과 구분할 수 없게 만드는 경로는 어디인가요?
- 운영자가 원인을 찾는 데 필요한 정보가 어느 지점에서 사라지나요?

#### 실행

payments와 admin의 try/catch, 기본 응답, 로그 흐름을 추적하고 실패 입력, 실제 오류, 외부 응답을 표로 기록합니다. 코드는 아직 바꾸지 않습니다.

#### 검증

- [ ] 두 fallback 위치가 파일과 라인으로 기록됐습니다.
- [ ] 숨겨지는 오류 정보가 기록됐습니다.
- [ ] 현재 테스트가 놓치는 경로가 표시됐습니다.

### E2. Fallback 제거하기

#### 설계 질문

- 오류를 호출자에게 전달할지 HTTP 오류로 변환할지 어느 계층이 결정하나요?
- 기존 정상 응답의 계약을 바꾸지 않고 실패를 드러낼 수 있나요?

#### 실행

승인된 오류 처리 경계에 따라 두 fallback을 제거하고 필요한 테스트를 보강합니다. 새 기본값으로 대체하지 않습니다.

#### 검증

- [ ] payments 예외가 `ok:false` 성공 응답으로 삼켜지지 않습니다.
- [ ] admin 예외가 빈 배열 성공 응답으로 바뀌지 않습니다.
- [ ] 정상 결제와 정상 관리자 조회 테스트가 통과합니다.
- [ ] 실패 응답 또는 전파 경로를 테스트합니다.

### E3. Retry와 stop 기준 나누기

#### 설계 질문

- 같은 입력으로 다시 시도해 회복 가능한 실패는 무엇인가요?
- 정책, 데이터, 권한 문제처럼 사람 확인 없이 반복하면 안 되는 실패는 무엇인가요?

#### 실행

`docs/retry-stop-matrix.md`에 실패 종류, 감지 신호, 재시도 여부, 최대 횟수, 중단 뒤 행동을 정리합니다.

#### 검증

- [ ] retry와 stop 사례가 각각 두 개 이상 있습니다.
- [ ] 재시도 횟수 또는 종료 조건이 있습니다.
- [ ] 사람 확인이 필요한 실패가 표시됩니다.

### E4. Failure handling 체크리스트 만들기

#### 설계 질문

- 오류를 숨기지 않았음을 최종 검토에서 어떻게 확인할까요?
- 로그, 응답, 테스트, 중단 조건 중 빠진 층이 있나요?

#### 실행

`docs/checklists/failure-handling.md`에 오류 보존, 외부 응답, 로그, retry, stop, 테스트 항목을 작성하고 전체 검증 뒤 커밋합니다.

#### 검증

- [ ] 체크리스트가 여섯 항목 이상입니다.
- [ ] 실패 정보를 빈 값으로 바꾸지 않는 항목이 있습니다.
- [ ] 전체 test, lint, typecheck가 통과합니다.
- [ ] 변경 파일이 payments, admin, 관련 테스트와 두 문서로 제한됩니다.

## 5. 흔한 함정

- 기존 catch를 다른 기본값 반환으로 바꿉니다.
- 모든 실패를 무조건 재시도하게 합니다.
- 오류 메시지를 그대로 외부에 노출해 내부 정보를 새게 합니다.

## 6. 다음 강으로 넘기는 것

교정된 오류 처리와 retry-stop 기준은 16강 PR preflight의 실패 처리 항목이 됩니다. 관리자 실패 사유 필드는 17강까지 추가하지 않습니다.
