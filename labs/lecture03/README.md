# Lab 03 — 작업 경계 잡기

## 0. 이 랩이 끝나면

- 넓은 요청을 네 개의 작은 작업으로 나눕니다.
- 단계별 금지 조건, 사람 확인 지점, 멈춤 조건을 정의합니다.
- 보조 산출물 `notes/task-boundary.md`를 만듭니다.
- 예상 소요 시간은 40분입니다.

## 1. 시작 전 상태 확인

- Lab 02의 notes 파일 세 개가 존재해야 합니다.
- 앱 코드는 v0이며 변경할 계획이 없어야 합니다.
- 전제 파일이 없으면 `node labs/tools/check.mjs 02`부터 실행합니다.

## 2. 실습 목표와 산출물

| 단계 | 핵심 작업 | 결과 |
| --- | --- | --- |
| E1 | 넓은 요청을 목적과 종료 상태가 있는 네 작업으로 나눕니다. | `notes/task-boundary.md`의 요청 분해 표 |
| E2 | 각 단계에서 아직 하지 않을 일을 정합니다. | 같은 파일의 단계별 금지 조건 |
| E3 | 자동 진행 전에 확인받을 지점을 표시합니다. | 같은 파일의 Human Gate |
| E4 | 범위 이탈 시 멈출 조건을 완성합니다. | 같은 파일의 멈춤 조건과 완료 커밋 |

## 3. 실습

### E1. 요청을 네 작업으로 나누기

#### 설계 질문

- 탐색, 결정, 계획, 구현을 한 번에 처리하고 있지 않나요?
- 각 작업의 입력과 출력이 한 문장으로 구분되나요?

#### 실행

`notes/task-boundary.md`에 요청 분해 표를 만들고 네 작업의 목적, 입력, 종료 상태를 적습니다.

#### 검증

- [ ] 요청이 네 행으로 분리됐습니다.
- [ ] 각 행에 입력과 종료 상태가 있습니다.
- [ ] 네 작업 어디에도 구현이 들어 있지 않습니다.

### E2. 단계별 금지 조건 정하기

#### 설계 질문

- 탐색 단계에서 하면 안 되는 변경은 무엇인가요?
- 결정 전에는 어떤 파일을 만들면 안 되나요?

#### 실행

각 작업에 `아직 하지 말 것`을 추가합니다. 금지 조건은 행동과 대상이 함께 보이게 씁니다.

#### 검증

- [ ] 네 작업 모두 금지 조건이 있습니다.
- [ ] 금지 조건이 파일 또는 행동을 구체적으로 가리킵니다.
- [ ] 현재 작업 트리에 앱 코드 변경이 없습니다.

### E3. 사람 확인 지점 표시하기

#### 설계 질문

- 정책을 확정할 권한은 누구에게 있나요?
- 구현 전에 확인받지 않으면 되돌리기 비싼 지점은 어디인가요?

#### 실행

정책 선택과 구현 승인 지점을 human gate로 표시하고, 필요한 입력과 승인 결과를 적습니다.

#### 검증

- [ ] 사람 확인 지점이 두 곳 이상 있습니다.
- [ ] 각 지점에 확인할 질문이 있습니다.
- [ ] 승인 전 다음 단계로 넘어가지 않는 조건이 있습니다.

### E4. 멈춤 조건 완성하기

#### 설계 질문

- 정보 부족, 범위 초과, 검증 실패를 각각 어떻게 감지할까요?
- 멈춘 뒤 누구에게 무엇을 보고해야 하나요?

#### 실행

세 종류의 멈춤 조건과 보고 내용을 추가하고 파일 전체를 검토한 뒤 커밋합니다.

#### 검증

- [ ] 멈춤 조건이 세 종류 이상 있습니다.
- [ ] 각 조건은 참 또는 거짓으로 판정할 수 있습니다.
- [ ] 멈춘 뒤 남길 정보가 정의돼 있습니다.
- [ ] 앱 코드 diff가 없습니다.

## 4. Self-check

```bash
node labs/tools/check.mjs 03
```

보조 산출물이므로 파일 누락은 경고로 표시됩니다.

## 5. 자주 하는 실수

- 작업을 파일 목록으로만 나누고 종료 상태를 쓰지 않습니다.
- human gate를 모든 단계에 넣어 실제 판단 지점이 흐려집니다.
- 멈춤 조건을 `잘 안 되면`처럼 판정 불가능하게 씁니다.
