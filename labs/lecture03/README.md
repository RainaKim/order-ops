# Lab 03 — 작업 경계 잡기

## 0. 이 랩이 끝나면

- 넓은 요청을 네 개의 작은 작업으로 나눕니다.
- 단계별 금지 조건, 사람 확인 지점, 멈춤 조건을 정의합니다.
- 보조 산출물 `notes/task-boundary.md`를 만듭니다.
- 예상 소요 시간은 40분입니다.

## 1. 시작 전 상태 확인

- Lab 02의 notes 파일 세 개가 존재해야 합니다.
- 앱 코드는 v0이며 변경할 계획이 없어야 합니다.
- 전제 파일이 없으면 `node labs/tools/check.mjs 02`부터 실행합니다.

## 2. 실습 목표와 산출물

| 단계 | 핵심 작업 | 결과 |
| --- | --- | --- |
| E1 | 넓은 요청을 목적과 종료 상태가 있는 네 작업으로 나눕니다. | `notes/task-boundary.md`의 요청 분해 표 |
| E2 | 각 단계에서 아직 하지 않을 일을 정합니다. | 같은 파일의 단계별 금지 조건 |
| E3 | 자동 진행 전에 확인받을 지점을 표시합니다. | 같은 파일의 Human Gate |
| E4 | 범위 이탈 시 멈출 조건을 완성합니다. | 같은 파일의 멈춤 조건과 완료 커밋 |

## 3. 실습

### E1. 요청을 네 작업으로 나누기

#### 설계 질문

- 탐색, 결정, 계획, 구현을 한 번에 처리하고 있지 않나요?
- 각 작업의 입력과 출력이 한 문장으로 구분되나요?

#### 실행

`notes/task-boundary.md`에 요청 분해 표를 만들고 네 작업의 목적, 입력, 종료 상태를 적습니다.

```
목표: 「주문 상태 처리 개선해줘」 한 줄을 네 개의 작업으로 나눠
      notes/task-boundary.md의 ## 요청 분해에 표로 적는다
문맥: notes/next-actions.md의 ## 다음 작업
      notes/order-status-request.md의 ## 요청 원문 — 완료 조건 네 줄이 여기 있다
      notes/pending-decisions.md의 ## 결정이 필요한 질문
제약: 표의 열은 작업 · 목적 · 입력 · 종료 상태 네 개다
      각 작업은 탐색 · 결정 · 계획 중 하나여야 한다 — 구현은 넣지 않는다
      마지막 작업은 계획이다 — 앞의 조사와 결정을 받아 무엇을 어디까지 바꿀지 적는 작업
      종료 상태는 무엇이 남으면 끝인지로 쓴다 — 「정리한다」는 종료 상태가 아니다
      src/와 tests/는 열지 않는다
완료 조건: ## 요청 분해 아래 네 행이 있고, 행마다 입력과 종료 상태가 채워져 있다
```

#### 검증

- [ ] 요청이 네 행으로 분리됐습니다.
- [ ] 각 행에 입력과 종료 상태가 있습니다.
- [ ] 네 작업 어디에도 구현이 들어 있지 않습니다.

### E2. 단계별 금지 조건 정하기

#### 설계 질문

- 탐색 단계에서 하면 안 되는 변경은 무엇인가요?
- 결정 전에는 어떤 파일을 만들면 안 되나요?

#### 실행

각 작업에 `아직 하지 말 것`을 추가합니다. 금지 조건은 행동과 대상이 함께 보이게 씁니다.

```
목표: ## 요청 분해의 네 작업마다 「아직 하지 말 것」을 붙여
      notes/task-boundary.md의 ## 아직 하지 말 것에 적는다
문맥: notes/task-boundary.md의 ## 요청 분해
제약: 각 작업에서 막을 것은 그 작업의 다음 단계다 —
      탐색에서는 결정과 계획을, 결정에서는 계획을, 계획에서는 구현을 미리 하지 않는다
      네 금지 조건이 서로 달라야 한다 — 같은 문장을 네 번 쓰지 않는다
      금지 조건은 행동과 대상을 같이 쓴다 — 「조심한다」는 금지 조건이 아니다
      src/와 tests/를 고치지 않는 것은 오늘 전체 제약이라 작업별로 반복하지 않는다
      ## 요청 분해 표는 고치지 않는다
완료 조건: ## 아직 하지 말 것 아래에 네 작업이 다 있고, 네 조건이 서로 다르다
```

#### 검증

- [ ] 네 작업 모두 금지 조건이 있습니다.
- [ ] 금지 조건이 파일 또는 행동을 구체적으로 가리킵니다.
- [ ] 현재 작업 트리에 앱 코드 변경이 없습니다.

### E3. 사람 확인 지점 표시하기

#### 설계 질문

- 정책을 확정할 권한은 누구에게 있나요?
- 구현 전에 확인받지 않으면 되돌리기 비싼 지점은 어디인가요?

#### 실행

정책 선택과 구현 승인 지점을 human gate로 표시하고, 필요한 입력과 승인 결과를 적습니다.

```
목표: 자동으로 넘어가면 안 되는 지점을 골라
      notes/task-boundary.md의 ## Human Gate에 적는다
문맥: notes/task-boundary.md의 ## 요청 분해 · ## 아직 하지 말 것
      notes/pending-decisions.md의 ## 결정이 필요한 질문
제약: 게이트마다 세 가지를 같이 쓴다
      — 어느 작업 뒤인지 · 사람이 확인할 질문 · 승인 전에 하지 않을 것
      「어느 작업 뒤인지」는 ## 요청 분해의 작업 이름으로 쓴다 —
      다른 게이트를 가리키지 않는다
      질문에 답을 쓰지 않는다
      질문 하나에 결정 하나만 담는다 — 예/아니오로 닫히는 질문은
      답을 받아도 아무것도 골라지지 않는다
      같은 지점에서 물을 질문은 한 게이트에 모은다 —
      질문이 늘어도 게이트는 늘리지 않는다
      게이트는 되돌리기 비싼 지점에만 건다 — 사람을 부르는 건 공짜가 아니다
완료 조건: ## Human Gate 아래 게이트가 두 개 이상이고,
          ## 결정이 필요한 질문의 질문이 빠짐없이 어느 게이트엔가 들어가 있고,
          게이트마다 예/아니오로 닫히지 않는 질문과 승인 전 정지 조건이 있다
```

#### 검증

- [ ] 사람 확인 지점이 두 곳 이상 있습니다.
- [ ] 각 지점에 확인할 질문이 있습니다.
- [ ] 승인 전 다음 단계로 넘어가지 않는 조건이 있습니다.

### E4. 멈춤 조건 완성하기

#### 설계 질문

- 정보 부족, 범위 초과, 검증 실패를 각각 어떻게 감지할까요?
- 멈춘 뒤 누구에게 무엇을 보고해야 하나요?

#### 실행

세 종류의 멈춤 조건과 보고 내용을 추가하고 파일 전체를 검토한 뒤 커밋합니다.

```
목표: 사람이 안 보고 있을 때 스스로 서는 조건을 적고
      notes/task-boundary.md를 커밋한다
문맥: notes/task-boundary.md 전체
제약: 멈춤 조건은 정보 부족 · 범위 초과 · 검증 불가 세 종류를 다 쓴다
      조건마다 참인지 거짓인지 판정되게 쓴다 — 「잘 안 되면」은 조건이 아니다
      멈춘 뒤 남길 것을 같이 적는다
      — 어디까지 했는지 · 왜 멈췄는지 · 무엇이 있어야 재개되는지
      src/와 tests/는 바뀌지 않는다 · 커밋은 notes/task-boundary.md 하나만
완료 조건: ## 멈춤 조건 아래 세 종류가 다 있고, 조건마다 판정 기준이 붙어 있다
          node labs/tools/check.mjs 03이 통과한다 (파일 · 헤딩 넷 · src/tests 무변경)
```

#### 검증

- [ ] 멈춤 조건이 세 종류 이상 있습니다.
- [ ] 각 조건은 참 또는 거짓으로 판정할 수 있습니다.
- [ ] 멈춘 뒤 남길 정보가 정의돼 있습니다.
- [ ] 앱 코드 diff가 없습니다.

```bash
node labs/tools/check.mjs 03
```

## 5. 자주 하는 실수

- 작업을 파일 목록으로만 나누고 종료 상태를 쓰지 않습니다.
- human gate를 모든 단계에 넣어 실제 판단 지점이 흐려집니다.
- 멈춤 조건을 `잘 안 되면`처럼 판정 불가능하게 씁니다.
