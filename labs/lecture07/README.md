## 3. 실습

### E1. 주문 상태 정의와 전환 표 작성하기

Lab 05에서 선택한 상태 범위를 요청 하나의 결정으로만 남기지 않고 주문 도메인의 기준으로 승격합니다. 현재 코드의 상태값은 사실 확인에 사용하되, 현재 구현과 앞으로 지킬 정책을 같은 것으로 취급하지 않습니다.

#### 설계 질문

- `pending`, `paid`, `payment_failed`, `cancelled`, `refunded`의 의미와 진입 조건이 서로 구분되나요?
- 결제 성공·실패, 취소, 환불은 각각 어떤 전환을 일으키나요?
- `paid` 주문의 취소처럼 사람이 선택해야 할 전환은 무엇인가요?
- 종료 상태와 아직 결정하지 않은 전환을 구분했나요?

#### 실행

`notes/pending-decisions.md`, `notes/order-status-plan.md`, `src/store.ts`, `src/server.ts`를 읽고 현재 사실, 이미 선택한 정책, 이번 단계에서 새로 결정할 항목을 구분합니다. Sol에게 다섯 상태의 정의 후보와 전환표 후보를 먼저 대화에만 작성하게 합니다.

```text
목표: docs/order-policy.md에 상태 정의와 전환 조건을 작성한다.
문맥: @notes/pending-decisions.md, @notes/order-status-plan.md와 현재 코드 상태를 사용한다.
제약: 상태 이름은 다섯 개로 두고, ______ 전환은 사람 승인 전 확정하지 않으며 코드는 수정하지 않는다.
완료 조건: 상태마다 의미·진입 조건이 있고 전환마다 시작 상태·이벤트·종료 상태가 있다.
```

##### 사람 확인 — 상태 구조

파일을 쓰기 전에 상태 의미, 진입 조건, 허용 전환, 금지 전환, 보류 전환을 사람이 승인합니다. 특히 다음을 확인합니다.

- 결제 전·성공·실패·취소·환불이 서로 다른 상태로 설명되는가?
- `payment_failed`, `cancelled`, `refunded`를 종료 상태로 둘지 명시했는가?
- `paid` 이후 취소를 허용할지 환불로만 처리할지 사람이 선택했는가?
- 이번 구현에서 제외된 상태를 현재 구현된 기능처럼 표현하지 않았는가?

승인 후 Terra에게 승인된 내용만 `## 상태 정의`, `## 전환 조건`에 기록하게 합니다. Luna로 `git diff -- docs/order-policy.md`를 확인하고, 새로운 상태나 전환이 조용히 추가되지 않았는지 검토합니다.

#### 검증

- [ ] 상태 다섯 개에 의미와 진입 조건이 있습니다.
- [ ] 전환표에 시작 상태·이벤트·종료 상태가 있습니다.
- [ ] 허용·금지·보류 전환이 구분됩니다.
- [ ] 사람 승인 전 선택이 정책으로 확정되지 않았습니다.
- [ ] diff에 `docs/order-policy.md` 외의 변경이 추가되지 않았습니다.

### E2. 결제 원칙과 재고 원칙 분리하기

같은 사용자 흐름에 참여하더라도 결제 결과와 재고 수량은 서로 다른 정책이 책임집니다. Lab 05에서 선택한 결제 실패·재고 기준을 장기 원칙으로 승인하고, 재시도처럼 작업별 선택에 머물 수 있는 항목은 다시 확인합니다.

#### 설계 질문

- 결제 실패 때 어떤 정보와 주문을 보존해야 하나요?
- 결제 성공·실패와 재시도 가능 여부를 무엇으로 판정하나요?
- 재고를 검사하고 차감하는 시점은 언제인가요?
- 재고 부족과 음수 재고를 어떤 조건으로 차단하나요?

#### 실행

Sol에게 E1의 주문 전환과 `notes/pending-decisions.md`, `notes/order-status-plan.md`를 대조해 결제 원칙과 재고 원칙 초안을 분리하게 합니다. 결제 문서는 승인·실패·재시도와 실패 정보 보존을, 재고 문서는 가용성 검사·차감·미차감·부족 차단을 책임집니다.

```text
목표: 결제 원칙과 재고 원칙을 서로 다른 두 정책 문서로 작성한다.
문맥: @docs/order-policy.md와 Lab 05·06의 결정·계획 기록을 사용한다.
제약: ______ 정책은 사람이 확정하며, 두 문서에 같은 원칙을 복제하거나 코드를 수정하지 않는다.
완료 조건: 성공·실패·재시도와 재고 검사·변경·부족 차단을 각각 판정할 수 있다.
```

##### 사람 확인 — 결제와 재고 경계

사람은 결제 성공 후 재고 반영, 결제 실패 시 재고 미반영, 재고 부족 주문의 저장 전 차단, 음수 재고 금지, 실패 정보 보존 범위를 확인합니다. 재시도 허용 여부는 Codex가 현재 코드에서 추론하지 않고 사람이 최종 승인합니다.

승인 후 Terra에게 `docs/payment-policy.md`의 `## 결제 원칙`과 `docs/inventory-policy.md`의 `## 재고 원칙`을 작성하게 합니다. Sol로 결제 성공·실패·재고 부족 시나리오를 세 정책 문서에 적용해 상태 전환과 재고 결과가 충돌하지 않는지 확인합니다.

#### 검증

- [ ] 두 문서가 서로 다른 책임을 설명합니다.
- [ ] 결제 성공·실패·재시도 조건을 구분할 수 있습니다.
- [ ] 실패 때 보존할 정보가 판정 가능하게 적혀 있습니다.
- [ ] 재고 검사·변경 시점과 부족 차단 조건이 판정 가능합니다.
- [ ] 결제·재고 원칙이 주문 전환표와 충돌하지 않습니다.

### E3. 관리자 조회 기준 정하기

관리자 조회 기준은 별도 네 번째 정책이 아니라 주문 정책의 일부입니다. 새로운 화면을 설계하지 않고, 실패 주문을 운영자가 판단하는 데 필요한 정보와 노출하지 않을 정보를 정합니다.

#### 설계 질문

- 실패 주문을 식별하고 후속 조치를 판단하려면 어떤 정보가 필요한가요?
- 상태·금액·시각·실패 사유는 어떤 조건에서 표시해야 하나요?
- 카드 정보처럼 민감하거나 운영에 불필요한 값은 무엇인가요?

#### 실행

현재 `src/admin.ts`, 승인된 주문·결제 정책과 Lab 05 계획을 대조합니다. Codex가 필드 후보, 의미, 노출 조건, 제외 이유를 먼저 표로 제시하게 하고 사람이 범위를 확정합니다.

```text
목표: docs/order-policy.md에 관리자 조회 기준을 추가한다.
문맥: @docs/order-policy.md, @docs/payment-policy.md와 현재 관리자 조회 코드를 사용한다.
제약: ______ 정보는 제외하고, 새 정책 파일·UI 설계·코드 변경을 만들지 않는다.
완료 조건: 필수·조건부·제외 정보와 실패 주문 표시 조건을 판정할 수 있다.
```

##### 사람 확인 — 노출 범위

사람은 실패 주문의 표시 여부와 상태·금액·시각·결제 실패 사유의 노출 조건을 승인합니다. 카드 토큰·카드번호·내부 예외처럼 민감하거나 불필요한 값은 제외합니다. 승인 후 Terra에게 `## 관리자 조회 기준`만 추가하게 하고 Luna로 `git diff -- docs/order-policy.md`를 확인합니다.

#### 검증

- [ ] `## 관리자 조회 기준`이 있습니다.
- [ ] 필수·조건부·제외 정보가 구분됩니다.
- [ ] `payment_failed` 주문의 표시 조건이 있습니다.
- [ ] 민감 정보와 관리자 UI 요구가 포함되지 않았습니다.
- [ ] E3 diff는 `docs/order-policy.md`에 한정됩니다.

### E4. AGENTS.md에 정책 연결하고 새 Task에서 확인하기

정책 문서를 만들었더라도 다음 Task가 읽지 않으면 지속 기준으로 작동하지 않습니다. 정책 내용을 `AGENTS.md`에 복사하지 않고, 변경 영역에 따라 어떤 문서를 읽어야 하는지 연결합니다.

#### 설계 질문

- 주문 상태·결제·재고·관리자 변경 전에 각각 어떤 정책을 읽어야 하나요?
- 여러 정책에 걸친 변경은 어떤 문서를 함께 읽어야 하나요?
- 문서가 없거나 서로 충돌하면 어느 지점에서 멈춰야 하나요?

#### 실행

Terra에게 root `AGENTS.md`의 기존 섹션을 보존하면서 `Before Editing`에 세 정책 경로와 읽는 조건을 연결하게 합니다. 정책 누락·충돌·미결 사항이 있으면 코드 수정 전에 멈추고 사람에게 확인하도록 합니다.

```text
목표: AGENTS.md에 도메인 정책을 읽는 조건을 연결한다.
문맥: 세 정책 문서와 현재 AGENTS.md의 Before Editing을 사용한다.
제약: 정책 본문을 복제하지 않고 기존 섹션과 앱 코드를 보존한다.
완료 조건: 변경 영역별 정책 경로와 문서 누락·충돌 시 정지 조건이 있다.
```

##### 사람 확인 — 결정 기록과 자동 적용

`notes/pending-decisions.md`에 이번 lab에서 최종 승인한 질문의 선택 결과와 결정일을 기록합니다. 이후 Luna로 다음을 확인합니다.

1. `node labs/tools/check.mjs 07`을 실행합니다.
2. `git diff -- AGENTS.md docs notes/pending-decisions.md`로 문서 변경만 검토합니다.
3. 새 Task에서 정책 내용을 알려 주지 않고 주문 상태 변경 전에 무엇을 읽어야 하는지 묻습니다.
4. 새 Task가 `AGENTS.md`를 따라 관련 정책을 찾고 충돌 시 멈추는지 확인합니다.

Blind 확인이 실패하면 정책 내용을 프롬프트에 복사하지 않습니다. 원래 Task에서 누락된 경로나 읽는 조건만 수정하고 새 Task 확인을 반복합니다. 모든 확인이 끝나면 세 정책 문서, `AGENTS.md`, 결정 기록만 하나의 커밋으로 남깁니다.

#### 검증

- [ ] 세 정책 경로와 읽는 조건이 `Before Editing`에 있습니다.
- [ ] 정책 누락·충돌 시 사람 확인 전 코드 수정을 멈춥니다.
- [ ] 확정한 질문에 선택 결과와 결정일이 있습니다.
- [ ] `node labs/tools/check.mjs 07`이 통과했습니다.
- [ ] 새 Task가 프롬프트에 정책을 복사하지 않아도 관련 문서를 찾았습니다.
- [ ] `src/`와 `tests/` diff가 없습니다.
