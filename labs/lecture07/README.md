## 3. 실습

### E1. 두 근거를 병렬 조사하고 전이 정책 정하기

상태 전이표는 그림이 아니라 나중에 코드와 테스트가 지켜야 할 규칙입니다. 현재 구현과 승인된 결정을 한 agent가 섞어 읽지 않도록 근거를 두 갈래로 나눕니다.

상태 이름은 `pending`, `paid`, `payment_failed`, `cancelled`, `refunded`로 고정됩니다. 여기서 사람이 판단할 것은 이름을 새로 만드는 일이 아니라 각 상태의 의미와 전환 경계입니다.

#### 설계 질문

- 현재 코드의 상태·삭제 동작과 문서에서 승인된 목표 상태를 구분할 수 있나요?
- 실패 주문 삭제가 감사 추적, 같은 주문의 재시도 식별, 관리자 정산에 미치는 영향을 어떤 근거로 판단하나요?
- 어떤 전환을 허용·금지·보류할 것이며, 특히 `paid` 이후 취소를 어떻게 처리할 것인가요?

#### 실행

Codex에게 읽기 전용 subagent 두 개를 병렬로 요청합니다. 첫 agent는 `notes/`의 결정과 계획을, 둘째 agent는 `src/store.ts`, `src/payments.ts`, `src/admin.ts`의 현재 동작과 실패 주문 삭제의 기술적 대가를 조사합니다. 둘 다 파일을 수정하지 않고 근거 경로와 불일치를 반환해야 합니다.

```text
목표: 두 subagent로 주문 상태 정책의 문서 근거와 코드 근거를 병렬 조사한다.
문맥: agent A는 @notes/pending-decisions.md @notes/order-status-plan.md, agent B는 @src/store.ts @src/payments.ts @src/admin.ts를 읽는다.
제약: 정책을 선택하거나 파일을 수정하지 말고, 두 결과를 섞지 않은 채 근거와 충돌만 보고한다.
완료 조건: 각 결과의 출처와 상태·전환·삭제 영향이 비교 가능하다. 추가 판단 항목: 실패 주문 보존 이유
```

두 agent의 Task를 직접 열어 실제로 서로 다른 입력을 읽었는지 확인합니다. 통합 결과가 나오면 다음 결정을 말로 확정하고 한 줄 이유를 남깁니다.

- `paid` 이후 취소 또는 환불 경계: `______`
- 그렇게 정한 이유: `______`

결정 뒤 Codex에게 다섯 상태의 의미·진입 조건과 허용·금지·보류 전환표를 `docs/order-policy.md`에 작성하게 합니다. 작성이 끝나면 파일을 처음부터 끝까지 직접 읽습니다. 금지 전환 한 행을 골라 “이 행이 Chapter 3에서 어떤 거부 테스트가 되는가?”를 한 문장으로 설명합니다.

#### 검증

- [ ] 상태 다섯 개에 의미와 진입 조건이 있습니다.
- [ ] 전환표에 시작 상태·이벤트·종료 상태·허용 여부가 있습니다.
- [ ] 허용·금지·보류 전환이 구분되고 사람 결정의 이유가 남아 있습니다.
- [ ] 두 subagent가 독립된 근거를 읽었고 `src/`, `tests/`를 수정하지 않았습니다.

자기점검:

- 금지 전환을 실제 표에 적었나요? 적지 않았다면 미래의 거부 테스트도 사라집니다.
- `payment_failed` 보존 이유를 취향이 아니라 현재 삭제 동작의 기술적 대가로 설명할 수 있나요?
- 전환표가 바로 통과했다면 허용하지 않을 전환까지 충분히 반박했나요?

### E2. Plan mode로 결제와 재고 책임 나누기

결제 결과와 재고 수량은 같은 요청 흐름에 참여하지만 다른 정책이 책임집니다. 먼저 `/plan`으로 두 문서의 경계와 충돌 가능성을 검토하고, 승인 뒤에만 작성합니다.

#### 설계 질문

- 결제 문서와 재고 문서가 각각 단독으로 책임질 판단은 무엇인가요?
- 주문 전이표와 두 문서가 함께 읽혀야 하는 지점은 어디인가요?
- Lab 05의 재시도 결정을 장기 정책으로 승격할지 보류할지 어떤 근거로 판단하나요?

#### 실행

Composer에 `/plan`을 입력한 뒤 아래 계약 뼈대를 사용합니다. Plan mode가 제안한 파일별 책임, 중복 제거 방법, 충돌 검사를 검토하되 아직 편집을 허용하지 않습니다.

```text
목표: 결제 정책과 재고 정책을 분리해 작성할 접근을 먼저 계획한다.
문맥: @docs/order-policy.md와 @notes/pending-decisions.md @notes/order-status-plan.md를 사용한다.
제약: 파일을 수정하지 말고, 기존 재시도 결정을 `승격/보류 ______ / 이유 ______`로 평가한다.
완료 조건: 두 문서의 책임·공유 경계·충돌 검사·작성 후 검증이 구분된다.
```

계획에서 같은 원칙이 두 파일에 복제되거나 재시도 정책이 추정됐다면 해당 항목만 수정하도록 피드백합니다. 계획을 승인한 뒤에만 `docs/payment-policy.md`의 `## 결제 원칙`과 `docs/inventory-policy.md`의 `## 재고 원칙`을 작성하게 합니다.

두 문서를 처음부터 끝까지 직접 읽고, 결제 성공·결제 실패·재고 부족을 각각 대입합니다. 한 문서의 문장을 지웠을 때 다른 문서의 규칙까지 의미가 바뀐다면 책임 경계를 다시 검토합니다.

#### 검증

- [ ] Plan mode에서 편집 전 책임 경계와 충돌 검사를 승인했습니다.
- [ ] 두 문서가 성공·실패·재시도와 재고 검사·변경·부족 차단을 나누어 책임집니다.
- [ ] 기존 재시도 결정을 다시 선택하지 않고, 장기 정책 승격 여부와 이유를 사람이 판단했습니다.
- [ ] 두 문서를 끝까지 읽고 세 시나리오를 대입했습니다.

자기점검:

- 결제 성공 후 차감과 실패 시 미차감을 어느 문서가 판정하는지 바로 찾을 수 있나요?
- 한 문서만 고쳐도 다른 정책의 의미가 조용히 바뀌는 중복이 남아 있나요?
- 주문 전이표와 결제·재고 원칙이 같은 사건에 다른 결과를 말하지 않나요?

### E3. 관리자 조회 기준을 쓰고 `/review`로 반박하기

관리자 조회는 네 번째 정책 파일이 아니라 주문 정책의 한 관점입니다. 운영 판단에 필요한 정보와 노출하면 안 되는 정보를 정한 뒤, 작성 Task와 분리된 reviewer에게 반례를 찾게 합니다.

#### 설계 질문

- 실패 주문을 식별하고 후속 조치를 판단하는 데 필요한 최소 정보는 무엇인가요?
- 상태·금액·시각·실패 사유의 노출 조건을 판정할 수 있나요?
- 카드 정보나 내부 예외처럼 노출하지 않을 값을 명시했나요?

#### 실행

현재 `src/admin.ts`와 승인된 주문·결제 정책을 대조하고, 필수·조건부·제외 정보와 표시 조건을 `docs/order-policy.md`의 `## 관리자 조회 기준`에 추가하게 합니다.

```text
목표: order-policy에 관리자 조회 기준을 추가한다.
문맥: @docs/order-policy.md @docs/payment-policy.md와 @src/admin.ts를 사용한다.
제약: 노출 제외 정보는 ______이며, 새 정책 파일·UI·앱 코드를 만들지 않는다.
완료 조건: 필수·조건부·제외 정보와 payment_failed 주문 표시 조건을 판정할 수 있다.
```

작성된 세 정책 문서를 처음부터 끝까지 직접 읽은 뒤 `/review`를 실행합니다. uncommitted changes 중 정책 문서만 범위로 삼고 “문서 간 충돌, 판정 불가능한 표현, 민감 정보 노출, 전이표와 관리자 표시의 불일치”를 검토 기준으로 지정합니다.

Review는 파일을 수정하지 않습니다. finding마다 `수용 / 거절 / 보류`를 사람이 정하고 이유를 말합니다. 수용한 finding만 원래 Task에 좁게 수정 요청한 뒤 최종 문서를 다시 읽습니다.

#### 검증

- [ ] 관리자 조회 기준에 필수·조건부·제외 정보와 실패 주문 표시 조건이 있습니다.
- [ ] `/review`가 정책 문서만 대상으로 작업 트리를 바꾸지 않고 finding을 반환했습니다.
- [ ] finding별 처리 결과와 이유를 사람이 판단했습니다.
- [ ] E3 변경은 `docs/order-policy.md`의 해당 섹션에 한정됩니다.

자기점검:

- 노출 필드는 운영자가 실제로 판단하는 데 필요한 것만 남았나요?
- reviewer의 제안을 권위처럼 전부 반영하지 않고 근거로 선별했나요?
- 실패 주문은 보존하지만 카드 정보나 내부 예외는 새지 않나요?

### E4. AGENTS.md routing을 Memory 없는 새 Task에서 증명하기

정책을 만들어도 다음 Task가 찾지 못하면 지속 기준이 아닙니다. `AGENTS.md`에는 본문을 복제하지 않고 변경 유형별 정책 경로와 멈춤 조건만 연결합니다.

#### 설계 질문

- 주문 상태·결제·재고·관리자 변경은 각각 어떤 정책으로 routing되어야 하나요?
- 정책 문서가 없거나 서로 충돌하면 어느 행동 전에 멈춰야 하나요?
- blind 확인에서 이전 대화와 Memory의 도움을 어떻게 제거할 수 있나요?

#### 실행

Codex에게 root `AGENTS.md`의 기존 섹션을 보존하면서 `Before Editing`에 세 정책 경로와 읽는 조건을 연결하게 합니다. 정책 누락·충돌·미결 사항은 코드 수정 전에 사람에게 확인하도록 합니다.

```text
목표: AGENTS.md에 변경 유형별 정책 routing과 정지 조건을 연결한다.
문맥: 세 정책 문서와 현재 AGENTS.md의 Before Editing을 사용한다.
제약: 정책 본문을 복제하지 않고 기존 섹션과 앱 코드를 보존한다.
완료 조건: ______ 변경이 올바른 정책으로 연결되고 누락·충돌 시 편집 전에 멈춘다.
```

`/memories`에서 새 Task가 기존 local memories를 사용하지 않도록 설정한 뒤 새 Task를 만듭니다. 정책 파일명이나 경로를 알려 주지 않고, 주문 상태 변경 전에 읽을 기준과 멈춤 조건을 찾아 보고하게 합니다. Memory 제어가 없다면 새로운 CLI 세션을 사용하고 그 한계를 기록합니다.

새 Task가 정책을 못 찾으면 그 Task에 답을 알려 주지 않습니다. 원래 Task에서 `AGENTS.md` routing만 고친 뒤 blind 확인을 반복합니다. 이것은 지식 퀴즈가 아니라 `AGENTS.md`가 세션 시작 시 자동 주입되어 올바른 문서로 연결하는지 확인하는 검증입니다.

#### 검증

- [ ] 세 정책 경로와 변경 유형별 읽는 조건이 `Before Editing`에 있습니다.
- [ ] 정책 누락·충돌 시 사람 확인 전 코드 수정을 멈춥니다.
- [ ] 확정한 질문의 선택 결과와 결정일이 `pending-decisions.md`에 있습니다.
- [ ] Memory 없는 새 Task가 정책 경로를 다시 듣지 않고 관련 문서를 찾았습니다.
- [ ] `node labs/tools/check.mjs 07`이 통과하고 `src/`, `tests/` diff가 없습니다.

자기점검:

- blind 프롬프트에 정책 경로나 내용을 복사했나요? 그렇다면 자동 routing 검증이 아닙니다.
- 새 Task가 정책을 찾은 근거가 Memory가 아니라 `AGENTS.md`임을 설명할 수 있나요?
- 정책 본문을 `AGENTS.md`에 복제해 컨텍스트 예산을 낭비하지 않았나요?

## 4. Self-check

```bash
node labs/tools/check.mjs 07
git diff -- AGENTS.md docs notes/pending-decisions.md
git diff -- src tests
```

첫 명령은 정책 파일·필수 섹션·상태 이름·`AGENTS.md` 경로·결정일을 확인합니다. 두 diff는 문서 변경과 앱 코드 무변경을 사람이 직접 확인하는 독립 증거입니다.

## 5. 자주 하는 실수

- 병렬화할 필요가 없는 한 파일을 여러 subagent가 중복 조사합니다.
- Plan mode의 초안을 사람 승인 없이 바로 파일로 작성합니다.
- `/review` finding을 검토하지 않고 모두 반영합니다.
- blind Task에 정책 경로를 다시 알려 주고 자동 routing이 작동했다고 판단합니다.
