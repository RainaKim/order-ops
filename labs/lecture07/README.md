# Lab 07 — 도메인 정책 문서 만들기

## 0. 이 랩이 끝나면

- 주문 상태와 전환 조건을 기준 문서로 만듭니다.
- 결제와 재고 원칙, 관리자 조회 기준을 분리해 기록합니다.
- `docs/order-policy.md`, `docs/payment-policy.md`, `docs/inventory-policy.md`를 만들고 root `AGENTS.md`에 연결합니다.
- 예상 소요 시간은 45분입니다.

## 1. 시작 전 상태 확인

- 2강 `notes/pending-decisions.md`의 미결정 질문 세 개를 다시 읽습니다.
- `docs/templates/workflow-skeleton.md`는 있지만 정책 문서 세 개는 아직 없어야 합니다.
- 앱 코드는 v0이며 이번 강에서도 수정하지 않습니다.

## 3. 실습

### E1. 상태 정의와 전환 표 작성하기

#### 설계 질문

- 다섯 상태의 의미와 진입 조건을 서로 구분할 수 있나요?
- 허용하지 않을 전환과 사람이 결정할 전환은 무엇인가요?

#### 실행

pending 질문을 사람이 결정한 뒤 `docs/order-policy.md`에 `## 상태 정의`와 `## 전환 조건`을 작성합니다. 코드 구현은 시작하지 않습니다.

#### 검증

- [ ] 상태가 다섯 개 정의돼 있습니다.
- [ ] 각 상태에 진입 조건이 있습니다.
- [ ] 전환 표에 시작 상태, 이벤트, 종료 상태가 있습니다.

### E2. 결제와 재고 원칙 분리하기

#### 설계 질문

- 결제 실패 때 보존해야 할 정보는 무엇인가요?
- 재고를 줄이는 시점과 부족을 차단하는 시점은 언제인가요?

#### 실행

결제 판단은 `docs/payment-policy.md`, 재고 판단은 `docs/inventory-policy.md`에 기록합니다. 두 문서가 충돌하지 않는지 함께 검토합니다.

#### 검증

- [ ] 두 파일이 서로 다른 책임을 설명합니다.
- [ ] 성공, 실패, 재시도 조건이 구분됩니다.
- [ ] 재고 변경 시점과 부족 차단 조건이 판정 가능하게 적혀 있습니다.

### E3. 관리자 조회 기준 정하기

#### 설계 질문

- 운영자가 실패를 판단하려면 어떤 필드가 필요한가요?
- 민감하거나 불필요해 노출하지 않을 값은 무엇인가요?

#### 실행

`docs/order-policy.md`에 `## 관리자 조회 기준`을 추가하고 필드, 의미, 노출 조건을 정리합니다.

#### 검증

- [ ] 관리자 조회 기준 섹션이 있습니다.
- [ ] 필수 필드와 제외 필드가 구분됩니다.
- [ ] 실패 주문의 표시 기준이 있습니다.

### E4. AGENTS.md에 정책 연결하기

#### 설계 질문

- 어떤 코드 변경 전에 어느 정책 문서를 읽어야 하나요?
- 문서가 없거나 서로 충돌할 때 어디서 멈춰야 하나요?

#### 실행

root `AGENTS.md`의 `Before Editing`에 세 정책 문서와 읽는 조건을 연결하고 새 세션에서 참조 여부를 확인한 뒤 커밋합니다.

#### 검증

- [ ] 세 정책 문서 경로가 모두 연결됐습니다.
- [ ] 정책 충돌 시 사람에게 확인하는 규칙이 있습니다.
- [ ] `pending-decisions.md`의 세 질문에 결정 결과가 기록됐습니다.
- [ ] 앱 코드 diff가 없습니다.

## 5. 흔한 함정

- 관리자 정책을 별도 네 번째 파일로 만들어 산출물 지도를 바꿉니다.
- 상태 이름만 나열하고 전환 조건을 쓰지 않습니다.
- 문서를 쓰면서 코드 상태도 먼저 확장합니다.
