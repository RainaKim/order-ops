# Lab 13 — 환각 차단

## 0. 이 랩이 끝나면

- 존재하지 않는 API를 사용하는 패치를 검증 명령으로 찾아냅니다.
- 에러 원문을 근거로 패치를 되돌리고 Lab 12 코드 상태로 복귀합니다.
- `notes/error-log-l13.md`, `docs/checklists/hallucination-guard.md`를 만듭니다.
- 예상 소요 시간은 40분입니다.

## 1. 시작 전 상태 확인

- Lab 12 코드와 테스트, diff review가 모두 커밋돼 있어야 합니다.
- 백업 입력은 `labs/fixtures/l13-hallucinated-patch.md`입니다.
- 시작 시 작업 트리가 깨끗해야 합니다.

## 2. 실습 목표와 산출물

| 단계 | 핵심 작업 | 결과 |
| --- | --- | --- |
| E1 | 존재하지 않는 API를 사용한 패치를 작업 트리에 재현합니다. | 커밋하지 않은 실패 패치 |

## 3. 실습

### E1. 환각 패치 재현하기

#### 설계 질문

- 패치가 호출하는 함수와 타입이 실제 코드에 있나요?
- 모델의 설명과 실제 diff 중 무엇을 먼저 신뢰해야 하나요?

#### 실행

Codex에게 관련 코드를 충분히 읽지 않은 변경을 제안하게 합니다. 같은 현상이 나오지 않으면 fixture의 패치를 작업 트리에 재현하되 커밋하지 않습니다.

#### 검증

- [ ] 작업 트리에 의도된 실패 패치만 있습니다.
- [ ] 존재 여부를 확인하지 않은 식별자를 표시했습니다.
- [ ] 패치를 커밋하지 않았습니다.

### E2. 검증 명령으로 가짜 코드 잡기

#### 설계 질문

- typecheck와 test는 각각 어떤 종류의 오류를 보여주나요?
- 첫 실패 원문에서 가장 직접적인 원인은 무엇인가요?

#### 실행

타입 검사와 테스트를 실행하고 종료 코드, 명령, 첫 관련 에러를 `notes/error-log-l13.md`에 원문 그대로 기록합니다.

#### 검증

- [ ] 실행한 명령과 종료 코드가 기록됐습니다.
- [ ] 에러 메시지와 파일 위치가 기록됐습니다.
- [ ] 실패 결과를 성공처럼 요약하지 않았습니다.

### E3. 에러 근거로 패치 되돌리기

#### 설계 질문

- 최소 복구는 새 함수를 만드는 것인가요, 근거 없는 패치를 제거하는 것인가요?
- 복구 뒤 Lab 12 상태와 같은지 어떻게 확인할까요?

#### 실행

환각 패치만 되돌리고 타입 검사와 테스트를 다시 실행합니다. 전후 결과를 error log에 연결합니다.

#### 검증

- [ ] 환각 패치의 src diff가 0줄입니다.
- [ ] 타입 검사와 테스트가 다시 통과합니다.
- [ ] Lab 12의 의도된 코드 변경은 유지됩니다.

### E4. Hallucination guard 만들기

#### 설계 질문

- 외부 API, 내부 함수, CLI 옵션을 사용하기 전에 무엇을 확인해야 하나요?
- 확인할 수 없는 내용은 어떤 상태로 남겨야 하나요?

#### 실행

`docs/checklists/hallucination-guard.md`에 탐색, 출처, 실행, 에러 기록, 확인 필요 표시의 점검 항목을 작성하고 커밋합니다.

#### 검증

- [ ] 체크리스트가 다섯 항목 이상입니다.
- [ ] 코드 존재 확인과 실행 검증이 분리돼 있습니다.
- [ ] 확인하지 못한 항목을 표시하는 규칙이 있습니다.
- [ ] 이 lab의 커밋에 src 변경이 없습니다.
